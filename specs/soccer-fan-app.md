# サッカー推し活アプリ 企画・仕様メモ

作成日: 2026年9月19日
状態: 企画段階のたたき台。ここに書いた機能をすべて実装する前提ではない。

> このファイルは `published: false` にしてあるので GitHub Pages には出ない。
> ただしリポジトリ自体は公開なので、公開したくない内容(収益の数字など)は書かないこと。

---

## 0. 結論の要約

- **コンセプトの核は「試合そのもの」ではなく「自分がその試合をどう見たか」の記録。** 速報・スタッツは既存アプリ(FotMob、Club J.LEAGUE 等)に任せ、感想・写真・満足度など「自分側のデータ」に全振りする。これが差別化になる。
- **最小構成はサーバーなし・API契約なし。** 日程と結果はユーザーが入力し、アプリは「入力を極限まで軽くする」ことに集中する。継続費用は Apple Developer Program の年会費だけになる。
- **Jリーグの日程・結果を自動取得する手段は、無料で安心して使えるものが今回の調査では見つからなかった。** 有料APIならある(月額 $10〜€29 程度の報告)が、利用規約は未確認。公式サイトの iCal は「転載・再配布・使用許諾不可」と記載されており、アプリが取得して配る用途には使えないと考えるべき。
- **チームロゴ・選手写真は初期リリースでは使わない。** Jリーグは「私的使用以外は許可制」、App Store も 5.2.1 でスポーツロゴのリジェクトが多い。チームカラー + ユーザーが決めた呼び名で「推し感」を出す。
- **複数チームはデータ構造だけ対応しておき、UIは1チームで出す。** 後から「推しを増やす」を有料機能にできる。
- **収益化は無料 + 買い切りアンロックを推奨。** 広告は推し活体験と相性が悪い。サブスクは自動取得(API費用)を載せるときに初めて検討する。

## 1. ユーザー体験と差別化

### 1.1 誰のためのアプリか

- 推しチームが1つある(多くて2〜3)。
- 現地にも行くが、DAZN・テレビで見る試合の方が多い。
- 試合ごとに何か書き残したいが、SNSに毎回投稿するほどではない。
- 「今シーズン何試合見たか」「あの試合はいつだったか」を思い出したくなる。

Club J.LEAGUE(公式アプリ)にもチェックインと観戦記録があるが、メダル・ポイント・抽選が主目的で、感想や写真をためる場所ではない。FotMob や SofaScore はデータは豊富だが「自分の記録」は残らない。ここが空いている。

### 1.2 体験のループ

```
試合前   ホーム画面に「次の試合まで ○日」と対戦相手 → 通知
   ↓
観戦     現地 / テレビ / 配信
   ↓
記録     「見た」を1タップ → 観戦方法を選ぶ → 一言(任意) → 写真(任意)
   ↓
振り返り タイムライン、シーズン集計、年間ベストゲーム
   ↓
次の試合が待ち遠しくなる
```

記録の入口を「一言だけでも成立する」ようにする。詳しく書きたい人には後から追記できる項目(MVP、満足度、印象的な場面)を用意する。

### 1.3 差別化の柱

| 柱 | 内容 | 既存アプリとの違い |
|---|---|---|
| 自分側の記録 | 感想、写真、チケット、満足度、自分MVP | 公式アプリはポイント目的、速報アプリは記録なし |
| 現地も配信も同じ扱い | 観戦方法をタグとして持つだけ。どちらも「見た」 | 公式のリモートチェックインは週の回数上限つき |
| 積み上がる感覚 | シーズン集計、通算観戦数、年間まとめ | 推し活アプリの「積み上げ」をサッカーに持ち込む |
| 一人で完結 | アカウント不要、端末内保存、SNS不要 | 開発者の既存アプリ(バイヤーノート、VINFIT)と同じ思想 |
| 推しの色に染まる | チームカラー2色でホーム画面・ウィジェットが変わる | 汎用アプリは白黒 |

## 2. 仕様を詰めたい点への回答

### 2.1 対象リーグと国内/海外の範囲

**推奨: 国内(J1・J2・J3)を主対象にしつつ、データ自動取得に依存しない設計にする。**

理由:

- 想定ユーザー(日本の推し活層)はJリーグが中心。
- ところが調査した限り、Jリーグは無料で使える日程・結果APIが最も乏しいリーグでもある。海外主要リーグは無料枠で日程・結果が取れる(2.3参照)。
- この矛盾を解くには「日程・結果はユーザーが入れるもの」を基本にし、自動取得は後から足す。手入力前提で気持ちよく使えるなら、海外リーグ・代表戦・カップ戦・地域リーグにも自然に対応できる。

つまり初期リリースでは「対象リーグ」という概念をアプリに持たせない。チーム名とチームカラーをユーザーが決めれば、どこのリーグでも記録できる。

代替案として「海外主要リーグ先行(football-data.org 無料枠で自動取得)」も検討したが、国内ファンという主戦場を外すので見送りを推奨する。技術検証には向くので、自動取得を実装するときの最初の対象にはなりうる。

### 2.2 推しチームを複数登録できるようにするか

**推奨: データ構造は最初から複数対応、UIは初期リリースで1チーム。**

- すべての記録に `teamId` を持たせておく。後から複数対応にするときにデータ移行が不要になる。
- 初期は「推しを変更」だけできる。変更しても過去の記録は元のチームに紐づいたまま残す。
- 「推しを追加」は買い切りアンロックの候補(3.4参照)。
- 複数対応にしたとき、ホーム画面は「メインの推し」の色で染め、切替はタブかヘッダーで行う。カウントダウン・集計はチームごと。

### 2.3 試合日程・結果の取得方法、API費用、利用条件

**注意: 以下は 2026年9月19日時点の検索結果に基づく。各サービスの公式ページには作業環境のネットワーク制限で直接アクセスできなかった。実装前に必ず一次資料(公式の料金ページと利用規約)を確認すること。** 「未確認」と書いた項目は、契約や実装の判断材料にしない。

#### 候補の比較

| 提供元 | 無料枠 | Jリーグ | 費用の目安 | 利用条件で注意すべき点 |
|---|---|---|---|---|
| football-data.org | 12大会(欧州主要リーグ、ブラジル1部、W杯、EURO)、10リクエスト/分、日程・結果・順位のみ | 無料枠に含まれない | 上位プランは €12/月〜という報告(未確認) | 商用可否・帰属表示の条件は未確認 |
| API-Football (api-sports.io) | 100リクエスト/日 | 全大会対象とされる | $10/月〜 | **無料枠は過去シーズン(2022〜2024)限定で当該シーズンは取れないという報告あり。** 実質、現在の日程は有料。規約は未確認 |
| TheSportsDB | v1 API、30リクエスト/分、コミュニティ編集のデータ | J1のリーグページあり(網羅性・正確性は未確認) | Premium $9/月で v2 と本番キー | 帰属表示が必要。商標ロゴは無加工で使うことという条件あり。データ精度はコミュニティ依存 |
| Sportmonks | デンマーク1部・スコットランド1部のみ | 有料プランで選択可 | Starter €29/月(5リーグ) | 規約は未確認 |
| Jリーグ公式 | 公開APIは見つからず。クラブ別の iCal ファイルを公式サイトが配布 | 当然あり | 無料 | **「ダウンロードしたデータの一部または全部を転載・再配布及び使用許諾を行うことはできません」と記載されている。** アプリが取得して利用者に配る形は不可と考える |
| Jリーグ公式サイト/データサイトのスクレイピング | - | - | - | 無断転載禁止の規約あり。個人開発でも採らない |
| データスタジアム等の商用データ提供 | - | あり | 個人には現実的でない金額と想定(未確認) | - |

#### 判断

1. **初期リリースは自動取得なし。** 日程・結果・スコアはユーザーが入力する。
2. **入力の軽さで自動取得の不在を補う。**
   - 対戦相手は入力履歴から補完(同じ相手はシーズンに2回以上ある)。
   - スコアは 2つの数字ステッパー、勝敗は自動判定。
   - 日付は「今日」「昨日」がワンタップ。
3. **自動取得を足すときの候補順:** 海外は football-data.org の無料枠で検証 → Jリーグは有料APIの規約を確認したうえで、月額を賄える課金設計と一緒に導入。
4. **Jリーグ公式 iCal の扱い:** アプリが代理取得するのは避ける。「ユーザー自身が公式サイトから自分の iPhone カレンダーに入れた予定を、アプリが EventKit で読む」設計なら開発者による再配布には当たらないと考えられるが、ここは法務的に断言できないので、実装前に規約本文を読み、必要なら問い合わせる。当面は候補にとどめる。

### 2.4 自動取得する部分と手動入力できる部分

| データ | 初期リリース | 将来(自動取得導入後) |
|---|---|---|
| 推しチーム名・略称・カラー | 手動(プリセット候補は 2.5 の判断次第) | 同じ |
| 試合日時・対戦相手・ホーム/アウェイ・大会名 | 手動。カレンダー読み取りは検討中 | APIから取得、手動で上書き可 |
| スコア・勝敗 | 手動(勝敗は自動計算) | APIから取得、手動で上書き可 |
| 観戦方法(現地/テレビ/配信/見てない) | 手動 | 手動 |
| 一言・感想・写真・チケット | 手動 | 手動 |
| 自分MVP・満足度・印象的な場面 | 手動 | 手動(選手名の候補提示はAPI次第) |
| シーズン集計・年間まとめ | 記録から自動算出 | 同じ |
| 通知 | 登録済みの試合から端末内でローカル通知 | 同じ |

原則: **自動化するのは「試合の事実」だけ。「自分の気持ち」は常に手動。** そして自動取得したものは必ず手動で直せるようにする(APIの誤りや延期に備える)。

### 2.5 チームロゴや選手画像などの扱い

**推奨: 初期リリースではロゴ・エンブレム・選手写真・マスコットを一切使わない。**

根拠(検索ベース、原文は要確認):

- Jリーグの「プロパティ利用規約」では、リーグとクラブのロゴ・エンブレム・マスコット等の商標・意匠は「自己の私的使用目的を除き、許可なく使用することを禁止」とされている。App Store で配布するアプリは私的使用の範囲を超える。
- 選手の肖像も Jリーグとクラブが管理している。
- App Store 審査ガイドライン 5.2.1(知的財産)で、スポーツチーム・リーグのロゴを使ったファンアプリのリジェクト事例が複数報告されている。ロゴだけでなくチーム名の扱いまで指摘された例もある。
- TheSportsDB 経由のロゴ画像も「商標ロゴは無加工で」という条件がある程度で、商標権者の許諾を代替するものではない。

代わりにやること:

- **チームカラー**をメイン/サブの2色で持ち、ホーム画面・ウィジェット・アイコン風のバッジに使う。色そのものは商標登録の対象になりにくいが、「エンブレムそっくりの図形」は作らない。
- **呼び名はユーザーが入力する。** 初期値は空。正式名称でも愛称でも好きに決められる。
- **プリセット(クラブ名とカラーの一覧)を同梱するかは要判断。** 名称の事実的な使用はロゴより低リスクと考えられるが、審査でどう扱われるかは事例が割れている。同梱するなら「文字列と色だけ、ロゴなし」に限定し、リジェクト時にプリセットを外せるように実装を分離しておく。
- ユーザーが撮った写真(観戦写真、チケット)は本人のものなので、端末内に保存する分には問題にならない。ただしアプリ側が共有・公開機能を持つと話が変わるので、初期は共有機能を持たない。

## 3. 最小構成(初期リリース)の提案

### 3.1 実装しない前提の技術方針

- **サーバーなし、アカウントなし。** データは端末内(SwiftData)。バックアップは iCloud(CloudKit のプライベートDB、またはiCloudバックアップに任せる)。
- **外部APIなし。** 継続費用は Apple Developer Program のみ。
- **通知はローカル通知のみ。** プッシュサーバーを持たない。
- SwiftUI、SwiftData、PhotosPicker、UserNotifications、WidgetKit。EventKit は検討中の機能でのみ使う。

### 3.2 データモデル(たたき台)

```
Team
  id, name(呼び名), shortName, primaryColor, secondaryColor,
  isPrimary, createdAt

Match
  id, teamId, kickoffAt, opponentName, isHome,
  competitionName(任意), venueName(任意),
  goalsFor?, goalsAgainst?          // 未入力なら「これから」
  status: scheduled | played | postponed | cancelled
  source: manual | imported | api   // 将来の自動取得に備える

Viewing(観戦記録。Matchと1対1)
  id, matchId,
  method: stadium | tv | streaming | notWatched | unknown,
  oneLiner(一言), note(長文、任意),
  satisfaction 1..5(任意), myMvp(自由入力、任意),
  highlight(印象的な場面、任意),
  createdAt, updatedAt

Photo
  id, viewingId, kind: photo | ticket, localAssetRef, takenAt

派生(保存しない): シーズン集計、通算成績、年間ベストゲーム
```

- `Match` と `Viewing` を分けるのは、「日程は入れたが観戦記録はまだ」の状態を自然に表すため。
- `Match.source` を最初から持っておくと、自動取得を足したときに「APIが更新してよい行」と「ユーザーが手で直した行」を区別できる。
- シーズンは `kickoffAt` から算出する(Jリーグは暦年、欧州は跨ぎ年)。チームごとに「シーズン開始月」を持たせると両方に対応できる。

### 3.3 画面構成

タブは4つに絞る。

1. **ホーム**
   - チームカラー背景。次の試合(相手、日時、ホーム/アウェイ)とカウントダウン。
   - 直近の試合結果と自分の一言。
   - 今シーズンの観戦数と勝敗(小さく)。
   - 「試合を追加」ボタン。
2. **日程・結果**
   - 月またはラウンド順のリスト。過去は結果とアイコン(観戦方法)、未来は日程。
   - 試合をタップで詳細へ。未観戦の試合は「見た」ボタンが目立つ。
3. **記録(試合詳細)**
   - スコア入力、観戦方法、一言、写真、任意項目(満足度、MVP、印象的な場面)。
   - 一言だけ入れて閉じても保存される。
4. **振り返り**
   - シーズンごとの観戦数、現地/配信の内訳、観戦した試合の勝敗。
   - 写真グリッド。
   - 年間まとめ(シーズン終了後に「今年のベストゲーム」を自分で選ぶ)。
5. **設定**(タブではなく歯車)
   - 推しチームの編集、通知のタイミング、書き出し、プライバシーポリシー。

### 3.4 機能のスコープ分け

| 区分 | 機能 |
|---|---|
| **初期リリース(必須)** | 推しチーム登録(1チーム、名前と2色)/ 試合の手動登録 / スコアと勝敗 / 観戦方法 / 一言と長文メモ / 写真とチケット(1試合あたり数枚) / 日程・結果リスト / ホームのカウントダウン / 試合前ローカル通知(前日・当日) / シーズン集計(観戦数、勝敗) / iCloudバックアップ / データ書き出し(CSV + 写真) |
| **次のリリース候補** | 満足度・自分MVP・印象的な場面 / 年間ベストゲームと年間まとめ画面 / ホーム画面ウィジェット(カウントダウン) / 複数チーム / 自分のカレンダーからの日程読み取り(規約確認後) / 対戦相手の入力補完 |
| **自動取得を導入するとき** | 日程・結果のAPI連携(まず海外リーグで検証)/ 延期・変更の反映 / 通知の自動登録 |
| **やらない** | SNS投稿の必須化 / 他ユーザーとの交流 / ロゴ・選手写真 / 速報・ライブスコア / 広告 |

### 3.5 収益化

**推奨: 無料 + 買い切りアンロック(1回数百円〜千円程度)。**

- 無料で「1チーム、記録、集計」まで全部使えるようにして、まず習慣化してもらう。
- アンロックの候補: 推しチームの追加 / 写真枚数の上限解除 / テーマ(色の細かい調整、ダークモードの配色) / 年間まとめのPDF書き出し / ウィジェットの追加スタイル。
- 広告は入れない。推しの色で染めた画面に無関係な広告が出る体験は、このアプリの価値を直接削る。
- **サブスクは自動取得を導入するときだけ検討する。** API費用が月額で発生する機能をサブスク側に置けば、契約者数と費用が連動する。それまでは買い切りで十分。
- 端末内保存なので、課金はすべて StoreKit 2 で完結し、サーバーでの権利管理は不要。

### 3.6 継続費用の見積もり

| 項目 | 初期リリース | 自動取得導入後 |
|---|---|---|
| Apple Developer Program | 年額(既存アプリと共通) | 同じ |
| サーバー・DB | 0円 | 0円(APIをアプリから直接叩けるかは規約次第。キー秘匿のため軽いプロキシが要る可能性あり) |
| データAPI | 0円 | $10〜€29/月程度(未確認、規約次第) |
| 画像ストレージ | 0円(端末とユーザーのiCloud) | 同じ |

1. **Jリーグ プロパティ利用規約の原文**(aboutj.jleague.jp)。クラブ名の文字列だけを載せる場合の扱い、写真アプリでの私的使用の解釈。
2. **Jリーグ公式 iCal の利用条件の原文。** 「ユーザー自身が自分のカレンダーに入れたものをアプリが読む」構成が再配布に当たらないか。判断がつかなければ問い合わせる。
3. **API-Football の利用規約と無料枠のシーズン制限。** 現在シーズンが本当に有料限定か、モバイルアプリからの直接呼び出しとキャッシュが許されるか。

5. **TheSportsDB の J1 データ品質。** 実際の日程を数週間分照合してから判断する。
6. **App Store 審査 5.2.1 の最近の事例。** チーム名の文字列だけでリジェクトされた例の有無。プリセット同梱の可否はこれで決める。
7. **競合の再確認。** Club J.LEAGUE の観戦記録機能の現状、App Store で「観戦記録」「サッカー 日記」で出てくるアプリ。

## 5. 決めてほしいこと

1. **国内手入力ファースト**でよいか。それとも海外リーグ先行で自動取得を最初から載せるか。
2. **プリセット(クラブ名とカラーの一覧)を同梱するか**、完全にユーザー入力にするか。前者は初回体験がよいが審査リスクがある。
3. **収益化は買い切り**でよいか。サブスクを最初から想定するか。
4. **写真の保存先。** アプリ内にコピーする(書き出しが簡単、容量を食う)か、写真ライブラリへの参照だけ持つ(軽いが、写真を消すと記録から消える)か。既存アプリ(バイヤーノート)の方式に合わせるのが楽。
5. **アプリ名の方向性。** 「推し」「観戦」「日記」のどれを前面に出すか。ストア検索で拾われる語を含めたい。
