## 0. 要約（1ページ版）

- **中心価値【案】**: 「話す・撮る・送るだけで、予定とメモとやることに振り分け、**動かせない予定を軸に**毎日の段取りを整えてくれる秘書」
- **最初のターゲット【案】**: **シフト勤務で働きながら、資格の勉強や生活の段取りに追われている 20〜40 代**（看護・介護・販売・工場などの 2 交代・3 交代勤務）
- **最初に解決すること【案】**: ①シフト表をカレンダーに手入力する手間、②勤務パターン（日勤・夜勤・明け・休み）ごとに生活を組み立て直す手間、③思いついた予定・用事を書き留め損ねること
- **MVP【案】**: iPhone アプリ単体で、「入力ボタン（音声・文字・スクショ）→ 確認カード → 予定・やること・メモへ登録」、シフト取り込み、勤務パターン別ルーティーン、「今日」画面と朝の案内。**家族機能・ライフイベント・「秘書に頼む」の本格版は MVP に入れない**
- **収益【案】**: 記録と確認は無料。**「AI に考えてもらう・作ってもらう」ことを有料**（週の計画づくり、振り返り、相談・作成）。月額 500〜700 円前後を仮説として検証する
- **推奨する進め方【案】**: **iPhone 先行**。LINE は「入力と問い合わせの窓口」として第 2 段階で追加する（LINE の返信は通数にカウントされないが、通知を送るとカウントされるため）
- **開発前に検証すること【案】**: シフト表の読み取り精度、振り分け入力が習慣になるか、「頼る」と「管理される」の境目、有料機能への支払い意思。5〜10 人・2〜4 週間の手作業による検証（コンシェルジュ型）で確かめる

## 1. 中心価値の定義

### 1-1. 一文での定義【案】

> **「思いついたことを投げるだけで、予定・やること・記録に振り分け、動かせない予定を守りながら、今日の段取りを一緒に整えてくれる秘書」**

ほかの言い方の候補:
- 短く言うと「投げれば、整う。」
- 機能で言うと「入力の振り分け × 動かせない予定を軸にした段取り」

### 1-2. この定義にした理由【案】

構想には「予定管理」「メモ」「日記」「体調」「目標」「家族」「相談」が並んでいます。これらに共通して、ユーザーにとって一番面倒なのは **「どこに何を入れるか考えること」** と **「予定が崩れたときに組み直すこと」** です。

- 入口を一つにし、仕分けを秘書に任せる → 「秘書らしさ」を最初の 1 回で実感できる
- 勤務や通院などの**動かせない予定**を先に置き、勉強や買い物などの**動かせる予定**をその隙間に並べる → 「マネージャーらしさ」を圧迫感なく出せる

「目標」や「相談」は、この土台（入力の振り分けと段取り）の上に乗る機能として位置づけます。

### 1-3. 「頼れる存在」の約束（設計原則）【確定＋案】

| # | 原則 | 区分 |
|---|---|---|
| P1 | AI は**提案する**。**登録・変更・削除はユーザーが確認してから**反映する | 確定（「勝手に重要な予定を変更しない」） |
| P2 | 動かせない予定（勤務・通院・約束）は、AI の組み直しの対象にしない | 確定 |
| P3 | 通知の頻度と積極性はユーザーが選ぶ。初期設定は控えめにする | 確定＋案（初期値は案） |
| P4 | 実際に行っていない操作を「完了」と表示しない（「候補」「未確認」「要電話」と明記する） | 確定 |
| P5 | 「聞いてほしいだけ」を選んだときは、改善提案をしない | 確定 |
| P6 | 元の入力（音声の文字起こし、画像）を残し、AI の解釈と並べて見られるようにする | 案 |
| P7 | どの操作も 1 タップで元に戻せる（変更履歴を持つ） | 案 |

## 2. 最初のターゲットと利用場面

### 2-1. 候補の比較【案】

| 候補 | 困りごとの強さ | 既存アプリとの差 | 始めやすさ | 課題 |
|---|---|---|---|---|
| **A. シフト勤務者（20〜40 代）** | 高：毎月のシフト表を手入力し、夜勤明けなどの体調に合わせて生活を組む必要がある | 「シフト取り込み」と「勤務パターン別の生活設計」を一緒にするアプリは少ないと思われる【推測・競合は未調査】 | 高：成人で自分で課金を決められる | シフト表の形式が職場ごとにばらばら |
| B. 受験生 | 高 | 学習管理アプリが多数ある【推測】 | 低：未成年の同意・課金・保護者対応が必要 | 繁忙期が季節に偏る |
| C. 子育て中の親 | 高 | 家族共有カレンダーが多数ある【推測】 | 中 | 家族機能が前提になり MVP が大きくなる |
| D. 高齢の家族を見守る人 | 中〜高 | 服薬アプリ・見守りサービスがある【推測】 | 低：本人の同意・権限・安全面の設計が重い | 誤った安心感を与えるリスク |
| E. 一般の社会人（汎用） | 低〜中 | 既存カレンダーや AI アシスタントと競合する | 高 | 差が伝わりにくい |

### 2-2. 推奨: A「シフト勤務者」【案】

理由:
1. **困りごとが具体的で、最初の価値がすぐ伝わる**: 「シフト表を撮ったら 1 か月分がカレンダーに入った」は、1 回使えばわかる体験です。
2. **構想の中心と合っている**: 「動かせない予定を軸に、動かせる予定を並べる」を一番必要としている人たちです。
3. **次の段階に自然につながる**: 看護師・介護職の資格勉強、転職準備 →「目標」機能へ。夜勤による体調の変化 →「体調」記録へ。
4. **汎用アプリとの違いを出しやすい**: 「日勤」「夜勤」「明け」「休み」という言葉をそのまま理解してくれる秘書、という位置づけにできます。

> 大学入試は、目標機能の例としてとても良い題材です。ただし最初のターゲットにすると未成年対応が必要になるため、**目標機能の仕組みは入試にも使える形で作り、最初に届ける相手は「資格試験の社会人」にする**ことを提案します。

### 2-3. 代表的な利用場面（ペルソナ）【案】

**ペルソナ: Aさん（29 歳・病棟看護師・2 交代勤務・登録販売者の資格を勉強中）**

| 場面 | 今の困りごと | このアプリでの体験 |
|---|---|---|
| ① 月末、翌月のシフト表が LINE グループに写真で届く | 自分の行を探して、1 日ずつカレンダーに手入力する（15〜30 分）。修正版が来るとまたやり直し | 写真を共有 →「自分の名前」を 1 回指定 → 1 か月分の確認画面 →「登録」。修正版は**差分だけ**が表示される |
| ② 夜勤明けの朝 | 眠いのに、今日やることを考えないといけない | 「今日は明けです。予定は 14 時の歯医者だけ。勉強はお休みの設定です」と短い案内が届く |
| ③ 歩きながら思いつく | メモアプリとカレンダーを行き来するのが面倒 | 「来週水曜 15 時に美容院。帰りに洗剤」と話す → 予定 1 件と買い物 1 件の**確認カード**が出て、1 タップで登録 |
| ④ 急な残業で勉強できなかった | 計画が崩れて、そのまま諦めてしまう | 「今日の勉強 30 分は、土曜の午前に移しますか？」と**提案だけ**される。承認すると反映される |
| ⑤ 寝る前 | 日記を書く気力がない | 30 秒の音声で一言日記。「聞いてほしいだけ」モードなら短い共感だけを返す |

## 3. 機能の段階分け（MVP／次の段階／将来構想）

### 3-1. 共通の仕組み（最初に作る土台）【案】

「機能ごとに独立した仕組みを増やさず、共通の仕組みを使う」【確定】を実現するため、次の 5 つの部品を最初に作り、すべての機能をこの組み合わせで作ります。

```
 [入口]              [解釈]             [確認]            [保存]                 [活用]
 音声・文字 ─┐
 スクショ    ─┼─→ ① 受付箱 ─→ ② 振り分け ─→ ③ 確認カード ─→ ④ 共通データ ─→ ⑤ 段取りエンジン
 共有・LINE  ─┘   (元データ保存)  (AI/端末)   (修正→登録)     (予定/やること/     (固定枠と可動枠で
                                                               メモ/記録/目標)       今日・今週を組む)
```

| 部品 | 役割 | 使い回す先 |
|---|---|---|
| ① 受付箱 | どこから入った入力も、元の形（音声・画像・文字）のまま一度受け取る | 音声入力、スクショ、シフト表、LINE、共有 |
| ② 振り分け | 入力を「予定」「やること」「買い物」「メモ」「記録」に分け、日時・場所などを取り出す | すべての入力 |
| ③ 確認カード | 解釈結果を見せ、修正・登録・破棄を選んでもらう。**AI の出力は必ずここを通る** | 振り分け、シフト取り込み、組み直し提案、「秘書に頼む」の結果 |
| ④ 共通データ | すべての項目を同じ形式で持つ。種類・固定/可動・元入力・外部カレンダーとの対応・センシティブ区分を持つ | 全機能 |
| ⑤ 段取りエンジン | 固定枠（勤務・通院）を置き、可動枠（勉強・家事）を隙間に置く。崩れたら組み直し案を出す | 今日画面、ルーティーン、目標の週次計画 |

**共通データの形（概念）【案】**

| 項目 | 例 |
|---|---|
| 種類 | 予定 / やること / 買い物 / メモ / 記録（日記・体調・服薬）/ 目標の一歩 |
| 固定か可動か | 固定（勤務・通院・約束）/ 可動（勉強・家事）/ 未定 |
| 時間 | 日時、所要時間、準備時間、移動時間 |
| 関係 | 属する目標、元になった入力、関連する予定 |
| 出どころ | 手入力 / 音声 / 画像 / シフト取り込み / LINE / 外部カレンダー |
| 外部との対応 | 外部カレンダーの予定 ID、取り込み元（どのシフト表の何日か） |
| センシティブ区分 | なし / 体調 / 通院 / 服薬 など（AI に渡すか・通知に出すかをこの区分で制御） |
| 状態 | 候補 / 確定 / 完了 / 未実施（理由つき）/ 記録なし |

### 3-2. 段階分け【案】

**MVP（最初のリリース）: 「投げれば整う」と「シフト生活の段取り」を届ける**

| 機能 | 内容 | 構想上の番号 |
|---|---|---|
| 入力ボタン（常に表示） | 音声・文字・スクショ／写真から入力 | 2 |
| 振り分けと確認カード | 予定・やること・買い物・メモに分けて確認してから登録 | 2 |
| iPhone カレンダー連携 | 読み取りと書き込み（Google アカウントを iPhone に追加していれば Google の予定も対象）※要実機検証 | 1 |
| 固定／可動の区別 | 予定ごとに「動かせない」を設定。勤務は自動で固定 | 1 |
| シフト取り込み | 写真・スクショから自分の行を読み取り、確認して一括登録。修正版は差分を表示 | 3 |
| 勤務区分の設定 | 日勤・夜勤・明け・休みの時間と、日付をまたぐ勤務 | 3 |
| 勤務パターン別ルーティーン | 区分ごとに「勉強 30 分」「買い物」「休息」などの型を置く | 3 |
| 今日画面 | 今日の予定、やること、次の行動 | 1 |
| 朝の案内・事前通知 | 通知の強さを 3 段階から選ぶ | 1 |
| 一言日記（文字・音声） | 「聞いてほしいだけ／提案も欲しい」を選ぶ。元の音声・文章も残す | 4（一部） |
| 記録の検索 | キーワード検索 | 4（一部） |
| 変更履歴と取り消し | すべての登録・変更を 1 タップで戻せる | 基本方針 |

**次の段階（MVP の検証後、優先度順）**

| 順 | 機能 | 理由 |
|---|---|---|
| 1 | **目標（資格試験）と週次計画**（有料） | ターゲットの次の困りごと。段取りエンジンをそのまま使える |
| 2 | **週の振り返り**（日記・未実施の理由 → 翌週の計画案）（有料） | 目標と日記をつなぐ。有料価値の中心になる |
| 3 | **LINE 窓口**（入力・今日の予定の確認） | 入力の敷居をさらに下げる。§8 参照 |
| 4 | **秘書に頼む（文章作成と計画づくり）**（有料） | 最新情報を使わない範囲から始める。§6 参照 |
| 5 | 移動時間の自動確保 | 地図 API の費用がかかるため、手動の「移動 30 分」設定から始め、需要を見て自動化する |
| 6 | 体調記録（夜勤による睡眠・疲労、生理） | 必要な項目だけ有効にする。予測はしない |
| 7 | Google カレンダーとの直接連携・Web 版 | Android の人や PC で使いたい人向け |

**将来構想（需要と体制が整ってから）**

- 家族での見守り（服薬など）— §10-1 で理由を説明
- ライフイベント別のテンプレート（妊娠・出産・引っ越し・就職）
- 秘書に頼む: 最新情報の検索、お店の候補出し
- 秘書に頼む: 空席確認・予約（提携先の API がある場合だけ）
- Android 版
- 受験生向け（保護者との連携を含む）

### 3-3. 家族機能を MVP に入れるべきか【案: 入れない】

| 観点 | 評価 |
|---|---|
| ターゲットとの一致 | シフト勤務者の中心的な困りごとではない |
| 設計の重さ | 招待、同意、権限、同意の撤回、アカウント削除時の扱い、2 人以上への通知が必要。**サーバーと複数人のアカウントが前提**になり、MVP の構成が大きく変わる |
| 安全面の責任 | 「通知があるから大丈夫」と誤った安心感を与えると、実害につながり得る。§10-1 の状態の区別は、検証してから出すべき |
| 検証の順番 | 一人で使って価値があるかを確かめてから、共有に広げる方が失敗が少ない |

ただし、**データの形は最初から「誰の項目か」「誰に見せるか」を持たせておく**と、後で家族機能を足すときの作り直しが減ります。

## 4. あえて作らない機能と理由【案】

| 作らないもの | 理由 |
|---|---|
| AI が確認なしに予定を登録・変更・削除する機能 | 基本方針 P1。誤認識の被害が大きく、信頼を失う |
| 独自のカレンダー（既存カレンダーの置き換え） | ユーザーは既存カレンダーを使い続けたい。同期の二重管理のもとになる |
| 医学的な予測・判断（排卵日予測、体調の診断、服薬量の判断） | 医療機器・医療行為に関わるおそれがあり、責任を負えない。**記録と予定管理に限定する** |
| 友達との個人トークを読み取る機能 | LINE の公式 API ではできない（§8-3）。できたとしてもプライバシー上問題が大きい |
| 予約の代行・決済 | 提携と責任分担が必要。「予約した」と誤認させるリスクがある |
| 汎用の雑談チャット（無制限） | 費用が読めず、差別化にもならない。「秘書に頼む」は成果物型にする |
| 家計簿・ToDo のプロジェクト管理・習慣トラッカーの作り込み | 専用アプリが多数ある。機能が増えすぎる懸念（ご指摘）に直結する |
| SNS・コミュニティ機能 | 中心価値と無関係。見守りの負担が増える |
| ゲーム性の強いごほうび・連続記録の強調 | 「管理される圧迫感」につながりやすい。控えめな達成表示にとどめる |
| Android 版・Web 版（MVP 段階） | 一人〜少人数の開発では、iPhone に集中した方が品質を出せる（§8） |

## 5. 画面構成と主要な操作の流れ

### 5-1. タブ構成の提案【案】

仮案の 5 タブ（今日・カレンダー・目標・記録・秘書に頼む）は、MVP の時点では多すぎると考えます。**「秘書に頼む」はタブではなく入力の一種**、**「目標」は有効にした人にだけ出す**ことを提案します。

**MVP: 3 タブ ＋ 常に表示される入力ボタン**

```
┌──────────────────────────┐
│  今日  │ カレンダー │  記録  │   ← 3 タブ
└──────────────────────────┘
                 (＋) ← 入力ボタン（話す／撮る／書く）
```

**次の段階: 目標を有効にした人には「目標」タブが加わる（4 タブ）**

| 画面 | 役割 | 主な操作 |
|---|---|---|
| **今日** | 「次に何をすればいいか」がすぐわかる。秘書からの提案と確認待ちもここに出る | 予定・やることの確認、完了にする、組み直し提案の承認、朝の案内を読む |
| **カレンダー** | 予定・勤務・ルーティーンを月・週で見る。固定と可動が色で区別される | 予定の確認・編集、シフト取り込み、ルーティーンの設定 |
| **記録** | メモ・日記・買い物・（後に）体調。検索もここ | 検索、日記を書く・聞き返す、買い物リストの確認 |
| **目標**（次の段階） | 目標ごとの計画と週の進み具合 | 目標の登録、今週の計画の承認、週の振り返り |
| **入力ボタン** | すべての入口。「頼む」もここから | 話す・撮る・書く。内容が依頼なら「秘書に頼む」の流れに進む |
| **設定** | 通知の強さ、センシティブ情報の扱い、勤務区分、連携 | 右上のアイコンから開く |

「入力ボタン」から「記録してほしい」と「頼みたい」の両方を受けるのは、**入口を一つにする**という中心価値と同じ考え方です。頼みごと（有料）に進むときは、「これは『秘書に頼む』です。残り 12 回」のように、はっきり表示します。

### 5-2. 主要な操作の流れ【案】

**流れ①: 話して登録する（MVP の中心）**

```
入力ボタンを押して話す
 「来週水曜15時に美容院。帰りに洗剤を買うってメモして」
   ↓ 端末で文字にする → 振り分け
確認カード
 ┌ 予定  10/7(水) 15:00〜 美容院   [固定にする □]  所要: 1時間(推定)
 └ 買い物 洗剤   (ひも付け: 美容院の帰り)
 [登録] [直す] [やめる]        ← 推測した部分は色を変えて表示
   ↓ 登録
iPhone カレンダーに予定、アプリ内の買い物リストに洗剤
10/7 の美容院のあとに「洗剤を買う」を表示
```

**流れ②: シフトを取り込む**

```
シフト表の写真を共有 or 撮影
 → 初回のみ:「あなたの名前・行はどれですか？」（表の上でタップ）
 → 初回のみ: 記号の意味を確認「日＝日勤 8:30-17:30 / 夜＝夜勤 16:30-翌9:00 / 明＝明け / 休＝休み」
 → 1か月分の一覧（読み取りに自信がないマスは強調表示）
 → [カレンダーに登録]
修正版を取り込んだとき:
 → 「変更 2 件（12日: 日→夜、13日: 休→明）、追加 0、削除 0」の差分だけを表示 → [反映]
```

**流れ③: 予定が崩れたときの組み直し**

```
「残業で勉強できなかった」と入力、または勉強の予定が完了にならないまま時間が過ぎる
 → 今日画面に提案:「勉強 30 分を、土曜 10:00 に移しますか？ / 今週は省く / 自分で決める」
 → 選んだものだけ反映（勤務などの固定予定は動かさない）
```

**流れ④: 一言日記**

```
夜の通知（設定した人だけ）→ 30秒話す
 → 読みやすく整えた文章と、元の文字起こしを並べて保存
 → モード「聞いてほしいだけ」: 短く共感するだけ
    モード「提案も欲しい」: 週の振り返り（有料）の材料になる
```

## 6. 「秘書に頼む」の設計

### 6-1. 能力の分け方【確定の方針を具体化した案】

「文章生成」「最新情報の検索」「空席確認」「予約」を別の能力として分け、**画面上でもどこまでやったかを表示**します。

| 段階 | 能力 | できること | 画面の表示 | 提供時期【案】 |
|---|---|---|---|---|
| L1 | 条件の整理 | 少ない質問で条件（人数・予算・エリア・日時）を集める | — | 次の段階 |
| L2 | 作成（外部情報なし） | 案内文、お礼・断りの文、学校への連絡、準備リスト、時間割の型 | 「作成しました」 | 次の段階 |
| L3 | 調べる（Web 検索） | 最新のお店・イベント・商品情報を集めて比較する | 「候補（◯月◯日時点の公開情報。営業状況は未確認）」＋出典リンク | 将来 |
| L4 | 空き確認 | 提携先 API で空席を確認する | 「◯時点で空きあり（提携先確認）」 | 将来・提携次第【未確認】 |
| L5 | 予約 | 提携先 API での予約 | 「予約完了（予約番号）」※API の完了応答がある場合のみ | 当面作らない |

L4・L5 がない間は、「お店に電話して確認してください」「予約ページを開く」のように、**ユーザーが行う次の一歩**として表示します。

### 6-2. 飲み会の幹事の例（L1〜L3 の場合）【案】

1. 入力:「飲み会の幹事になった。3次会まで決めたい」
2. 条件確認（最大 5 問・選択式を中心）: 日付、人数、予算/人、エリア、苦手な食べ物や喫煙の有無
3. 成果物
   - 1〜3 次会の候補（各 2〜3 件、選んだ理由、予算の目安、出典リンク）
   - 移動を含む時間割（徒歩の時間は推定と明記）
   - 満席だった場合の代わりの候補
   - 参加者向けの案内文（LINE にそのまま貼れる形式）
   - 「確認すること」リスト（予約の電話、人数の確定）
4. 戻す: 決めた内容を**確認カード**経由で予定・やること・メモに登録

**文脈として使う情報**は、ユーザーがその場でチェックしたもの（「この日の予定」「好み：辛いもの苦手」など）に限定し、何を AI に渡したかを結果の下に表示します。

## 7. 無料と有料の境界、AI 利用枠

### 7-1. 境界の考え方【案】

> **「記録する・見る・自分で動かす」は無料。「AI に考えてもらう・作ってもらう」は有料。**
> ただし、入力の振り分けは中心価値そのものなので、無料でも十分に使える量を用意する。

| 機能 | 無料 | 有料（「秘書プラン」仮称） |
|---|---|---|
| 手入力・カレンダー連携・今日画面・通知 | 無制限 | 無制限 |
| 音声・文字入力の振り分け | 1 日 10 回程度【案】 | 実質無制限（公正利用の範囲） |
| スクショ・写真からの予定候補 | 月 10 回程度【案】 | 実質無制限 |
| シフト取り込み | 月 2 回（修正版 1 回を含む）【案】 | 実質無制限 |
| 勤務パターン別ルーティーン | ◯ | ◯ |
| 一言日記・検索 | ◯ | ◯ |
| 組み直しの提案 | 決まったルールによる提案（AI なし） | AI による提案（理由つき） |
| 目標と週次計画 | 目標 1 件・計画は自分で作る | AI が逆算して計画し、週ごとに調整 |
| 週の振り返り | — | ◯ |
| 秘書に頼む | お試し 3 回 | 月 30 回【案】 |
| LINE 窓口（入力・確認） | ◯ | ◯ |

### 7-2. AI 利用枠の見せ方【案】

- 利用枠は**トークン数ではなく「回数」**で見せる（「頼みごと 残り 12 回」）。ユーザーにわかる単位にする
- 1 回の重さに差がある処理（L3 の検索など）は、「2 回分を使います」と**事前に表示**する
- 枠を使い切っても、**無料機能は止めない**。記録と確認は常に使える
- 月の途中で足りなくなった人向けに、回数の追加購入を用意するかは、利用データを見てから決める

### 7-3. 価格の仮説【推測・要検証】

- 月額 480〜680 円、年額は 2 か月分程度の割引、という水準を仮説とします。根拠は、個人向けの生産性アプリや AI 機能付きアプリで一般に見られる価格帯という経験則で、競合価格は未調査です
- App Store での課金には Apple の手数料がかかります（年間の売上が一定額以下の開発者向けの小規模事業者プログラムでは 15%）【推測・最新条件は未確認】
- **1 ユーザーあたりの AI 原価を売上の 30% 以内**に抑えることを目安にします（§9 で試算）

## 8. 技術構成

### 8-1. API ／端末内の処理／自前実装の区別【案】

| 処理 | 端末内でできる（無料・速い・プライバシーに強い） | 外部 API が必要 | 自前で作る |
|---|---|---|---|
| 音声 → 文字 | ◯ iOS の音声認識（iOS 26 の SpeechAnalyzer は端末内で動作。初回は言語モデルのダウンロードが必要）【確認済】 | 精度が足りない場合のみ（外部の音声認識 API） | — |
| 画像 → 文字（OCR） | ◯ Vision フレームワーク（日本語は iOS 16 以降）【確認済】 | — | — |
| シフト表の**構造**の理解（行と列、自分の行、記号） | △ 端末の OCR だけでは表の構造を取るのが難しい【推測】 | ◯ 画像を読める AI（マルチモーダル）API | 記号辞書、日付をまたぐ勤務の計算、差分比較 |
| 入力の振り分け（予定／買い物など） | △ 簡単な日時の抽出はルールで可能。iOS の端末内 AI の活用は要調査【未確認】 | ◯ 小型で安価な AI モデル | 確認カード、共通データへの変換 |
| カレンダーの読み書き | ◯ EventKit（iPhone のカレンダー。iPhone に追加した Google・iCloud のカレンダーも含む）【推測・要実機検証】 | Google Calendar API（Web 版・Android 版を作るとき） | 対応表（二重登録の防止） |
| 通知 | ◯ ローカル通知（朝の案内・事前通知） | プッシュ通知（サーバーから送る場合。APNs 自体は無料【推測】） | 通知の強さの設定 |
| 段取り（固定／可動の配置、組み直し） | ◯ ルールで計算できる | AI（理由の説明、複雑な提案） | **ここが中核。自前で作る** |
| 目標の計画づくり・振り返り | — | ◯ 高性能な AI モデル | 目標の型（試験日・科目・教材）、週次の流れ |
| 最新情報の検索 | — | ◯ Web 検索 API | 出典と日時の表示 |
| 移動時間 | △ MapKit で経路と所要時間【推測・利用条件は未確認】 | Google Maps などの経路 API（有料） | — |
| LINE | — | ◯ Messaging API（＋アカウント連携に LINE ログイン） | 連携用のサーバー |
| データの保存・同期 | ◯ 端末内データベース | クラウド（iCloud／自前サーバー） | — |

**MVP はできるだけ端末内で処理し、AI API は「振り分け」と「シフト表の構造理解」の 2 か所に絞ります。** これで、サーバーの運用費と、センシティブ情報を外に出す量の両方を抑えます。

### 8-2. 構成図（MVP → 次の段階）【案】

```
MVP
 iPhone アプリ ──(EventKit)── iPhone カレンダー（iCloud / Google を含む）
     │
     └──(薄い中継サーバー)── AI API（振り分け・シフト表の読み取り）
          ※ APIキーをアプリに埋め込まないため、および利用回数の管理のために中継する

次の段階
 iPhone アプリ ─┐
 LINE 公式アカウント ─┼── アプリ用サーバー（ユーザーデータ・利用枠・課金状態）── AI API / 検索 API
 (Web 版)     ─┘                                        └── Google Calendar API
```

中継サーバーは、サーバーレス（リクエストが来たときだけ動く仕組み）で作れば、利用者が少ない間の固定費はほぼかからない見込みです【推測】。

### 8-3. LINE 公式 API でできること・できないこと

| 項目 | 内容 | 区分 |
|---|---|---|
| ユーザーが公式アカウントに送った文章・画像・音声を受け取る | できる。画像・音声などはメッセージ ID で取得でき、一定期間後に LINE 側で自動削除される | 確認済 |
| 送られたメッセージへの返信（応答メッセージ） | 送信通数にカウントされない | 確認済 |
| 公式アカウントから自発的に送る（プッシュ：予定通知・リマインダー） | 送信通数にカウントされる | 確認済 |
| 友達との個人トーク・グループトークを読み取る | 公式アカウントが参加していないトークは受け取れない。個人トークを読む公式 API はない | 推測（API の仕組み上。公式資料の明記箇所は未確認） |
| アプリのアカウントと LINE ユーザーをつなぐ | LINE ログインまたはアカウント連携の仕組みで可能 | 推測（具体的な手順は未確認） |

**料金プラン（日本）**【確認済・2026-09-24 時点、Web 検索による】

| プラン | 月額（税別） | 無料で送れる通数/月 | 追加送信 |
|---|---|---|---|
| コミュニケーション | 0 円 | 200 通 | 不可 |
| ライト | 5,000 円 | 5,000 通 | 不可 |
| スタンダード | 15,000 円 | 30,000 通 | 可。**2026-10-01 から** 20 万通までは 1 通 3 円、それ以上は 1 通 2.5 円 |

**設計への影響【案】**

- 毎朝の案内を LINE のプッシュで送ると、1 人あたり月 30 通。無料プランでは **6〜7 人**、ライトプランでも **約 160 人**で上限に届く計算になる
- そのため、**LINE は「入力と問い合わせ」（返信なので通数にカウントされない）を中心にし、定期的な通知はアプリの通知を基本にする**。LINE での通知は有料プランの特典にするか、1 日 1 通までに制限する

| 観点 | iPhone 先行 | Web 先行 | LINE 先行 |

## 9. 費用の要因

### 9-1. 費用要因の一覧【案】

| 要因 | 何で増えるか | 抑え方 |
|---|---|---|
| AI（文章） | 入力 1 回ごとの振り分け、計画づくり、振り返り、頼みごと。**渡す文脈の量**が一番効く | 振り分けは小型モデル。文脈は必要な分だけ渡す。共通の指示文をキャッシュする |
| AI（画像） | シフト表、スクショ、チラシ。画像の解像度で費用が変わる | 端末で OCR と切り抜きを先に行い、必要な部分だけ送る |
| 音声 | 外部の音声認識を使う場合、秒数に比例 | 端末内の音声認識を基本にする |
| Web 検索 | 検索 1 回ごとの従量制が一般的【推測】 | 有料機能（L3）だけで使う。結果を一定時間使い回す |
| 地図・経路 | 経路計算 1 回ごと【推測】 | 手動の移動時間設定から始める |
| LINE 通知 | プッシュ送信の通数（§8-3） | 返信中心の設計。通知はアプリで行う |
| サーバー | リクエスト数とデータ量 | MVP は中継のみ。データは端末と iCloud に置く |
| Apple の手数料 | 売上の 15〜30%【推測】 | 年額プランへの誘導 |

### 9-2. 1 ユーザーあたりの AI 原価の試算方法【推測】

AI の料金はモデルと時期で変わるため、ここでは**計算のしかた**を示します。実際の単価は、採用するモデルの公式料金表で確認してください【未確認】。

```
月の原価 ＝ Σ（処理の月間回数 × 1 回あたりの入力量と出力量 × モデルの単価）

例：無料ユーザー（想定）
  振り分け     1 日 3 回 × 30 日 ＝  90 回   … 小型モデル、入力約 1,500 字・出力約 300 字
  スクショ読取              月 4 回   … 画像 1 枚
  シフト取り込み            月 1〜2 回 … 画像 1 枚＋表の出力
例：有料ユーザー（想定）
  上記 ＋ 週次計画 4 回 ＋ 振り返り 4 回 ＋ 頼みごと 15 回（高性能モデル）
```

見立て【推測】: 無料ユーザーは小型モデル中心なら月数円〜数十円、有料ユーザーは高性能モデルの利用で月数十円〜百数十円程度に収まる可能性が高いです。MVP の前に、上の回数で実際に API を呼んで原価を測ることを §11 の検証項目に入れています。

## 10. リスクへの対策

### 10-1. 家族での共有（将来構想で実装する際の設計方針）【案】

| 課題 | 対策 |
|---|---|
| 本人の同意 | **本人が招待・承認する**。家族が一方的に登録できない。何を共有するかを項目ごとに本人が選ぶ |
| 権限 | 「見るだけ」「記録できる」「予定を編集できる」を分ける。同意はいつでも撤回でき、撤回すると共有は即時に止まる |
| 「記録なし」と「飲んでいない」の区別 | 状態を 4 つに分ける：**予定どおり／記録済み（飲んだ）／記録済み（飲まなかった・理由）／記録なし**。通知の文面も「服薬の記録がまだありません」とし、「飲み忘れています」とは書かない |
| AI の判断 | 飲み忘れたときの対応・量の調整は**表示しない**。「処方した医師・薬剤師の指示に従ってください」と案内し、あらかじめ本人や家族が登録した指示だけを表示する |
| 誤った安心感 | 「このアプリは見守りの補助で、安全を保証するものではない」ことを初回と設定画面で明示する |
| 通知が届かない | 通知の失敗は検知しにくい【推測】。重要な服薬は複数の手段（アプリ通知＋LINE など）を本人が選べるようにする |

### 10-2. センシティブな記録【案】

- 健康に関する情報は、個人情報保護法の「要配慮個人情報」に当たり得るため、取得時に本人の同意が必要になると考えられる【推測・法的な確認は未実施。公開前に専門家への確認を推奨】
- **区分ごとの 3 つのスイッチ**（体調・通院・服薬・生理など、区分ごとに設定）
  1. **AI に使う**（オフなら、振り分け・計画づくりに一切渡さない）
  2. **通知に内容を出す**（オフなら「予定があります」とだけ表示。ロック画面で内容が見えない）
  3. **LINE で扱う**（オフなら LINE 経由の入力・表示をしない）
- 初期値はすべて**オフ**。有効にするときに、何が起きるかを一文で説明する
- 保存は端末と iCloud を基本にし、サーバーには残さない（AI への送信は処理のためだけに行い、保存しない設定の API を選ぶ）【案・API ごとのデータ保持条件は未確認】
- 記録画面の表示に、生体認証によるロックを任意で付けられるようにする
- 既存のプライバシーポリシーと同様に、「何を・どこへ送るか」を同意画面とポリシーで一致させる

### 10-3. 誤認識【案】

| 対策 | 内容 |
|---|---|
| 必ず確認してから登録 | AI の結果は確認カードを通す（P1） |
| 推測部分の強調 | 入力に書かれていなかった値（終了時刻、年、所要時間）は色を変えて「推定」と表示する |
| 元データの保存 | 元の音声の文字起こしや画像を横に並べ、見比べられる |
| 曖昧さの確認 | 「来週水曜」が 2 通りに解釈できる場合（週の始まりが日曜か月曜か）は、日付を明示して確認する |
| 学習 | ユーザーの修正内容（「美容院は 90 分」など）を、その人の設定として覚える |
| シフト表 | 自信の低いマスを強調表示。初回は 1 か月分を目で確認してもらう。記号の辞書は人が確認して登録する |
| 取り消し | 登録後も 1 タップで元に戻せる |

### 10-4. 二重登録【案】

| 場面 | 対策 |
|---|---|
| アプリが作った予定 | 自前の対応表（アプリの項目 ↔ カレンダーの予定 ID）を持つ。加えて予定のメモや URL 欄に目印を入れ、ID が変わっても見つけられるようにする（iPhone のカレンダーの予定 ID は同期で変わることがある【推測・要実機検証】） |
| シフトの修正版 | 「どのシフト表の、何日の勤務か」を鍵にして、**上書き**として扱う。登録前に「追加・変更・削除」の差分を表示する |
| 同じ内容を別の経路から入力（アプリと LINE など） | 日時と題名が近い予定があれば「すでに似た予定があります」と確認する |
| 外部で編集された予定 | 外部での変更を優先し、アプリ側で勝手に上書きしない |

## 11. 開発前に検証すべき仮説と方法

### 11-1. 仮説【案】

| # | 仮説 | 外れたときの影響 |
|---|---|---|
| H1 | シフト勤務者は、シフト表の手入力に毎月はっきりした手間を感じており、取り込み機能を使い続ける | ターゲットを見直す |
| H2 | 実際のシフト表の 8 割以上で、確認・修正 1 分以内の精度で読み取れる | 取り込み方式を見直す（テンプレート登録など） |
| H3 | 「話して振り分け」は、最初の 2 週間で 1 日 1 回以上使われる | 入力方式の優先度を下げる |
| H4 | 勤務パターン別ルーティーンと組み直しの提案は、「管理されている」ではなく「助かる」と感じられる | 提案の頻度・言い方を変える |
| H5 | 週次計画・振り返り・頼みごとに、月 500 円前後を払う人が一定数いる | 収益モデルを見直す |
| H6 | 無料ユーザーの AI 原価が月数十円以内に収まる | 無料枠を見直す |

### 11-2. 少人数での検証方法【案】

**参加者**: シフト勤務者 5〜10 人（知人の紹介、看護・介護のコミュニティなど）。謝礼は Amazon ギフト券 1,000〜2,000 円程度を想定【推測】。

| 週 | 内容 | 確かめる仮説 |
|---|---|---|
| 準備 | 参加者から実際のシフト表（名前を伏せたもの）を 10〜20 枚集め、AI API に読ませて精度を測る。同時に API の原価も測る | H2・H6 |
| 1〜2 週 | **LINE での手作業代行（コンシェルジュ型）**: テスト用の LINE 公式アカウントに、予定・メモ・シフト表を送ってもらう。開発者（＋AI の下書き）が振り分け、確認文を返し、承認されたら共有カレンダーに登録する | H1・H3 |
| 2〜3 週 | 朝の案内と組み直し提案を手作業で送る。通知の強さを「控えめ／ふつう／しっかり」から選んでもらう | H4 |
| 3〜4 週 | 資格勉強中の人に、週次計画と振り返りを手作業で作って渡す。最後に「月いくらなら払うか」と、実際の事前申し込み（予約）の有無を聞く | H5 |
| 終了時 | 30 分のインタビュー。「やめてほしかったこと」「なくなったら困るもの」を中心に聞く | 全体 |

**判断の目安（案）**
- H1・H3: 半数以上が 2 週間後も週 3 回以上送ってくる
- H2: 修正なし、または修正 1 分以内のシフト表が 8 割以上
- H5: 3 割以上が「払う」と答え、そのうち半数以上が事前申し込みをする

検証用の LINE 公式アカウントは無料プラン（返信は通数にカウントされない、プッシュは月 200 通まで）で足りる見込みです【確認済の料金条件に基づく推測】。
