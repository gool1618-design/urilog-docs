# ピクモグ 企画・仕様 第4版

> **ピクモグ | 今日の献立をピックに**

- 対象: iPhone(iOS 17以降を想定)
- 状態: 第4版(2026-09-22)。決定の流れを「**タップしたら決まり、いつでも選び直せる**」に簡略化し、判断の軸(§1)と、Codex の改善案の採否(§14)を足した。
- 第3版: **「今日なに食べるかを決めること」だけに特化する**方針に切り替えた。レシピ(分量・手順)はアプリから外し、作り方は外部に任せる。二人モードは家族(2〜6人)に一般化した。
- 前提: 個人開発。運用負担と継続費用を最小にする。外部サービスの写真・レシピは取得・転載しない。共有データは契約済みの Supabase に置く。

---

## 1. 位置づけ

**「今日なに食べよう?」を終わらせるボタン。** レシピアプリではない。

レシピを知っている人でも晩ごはんに悩むのは、料理を知らないからではなく、**今日の事情(食べたいもの・時間・手間・疲れ・最近食べたもの・家族の希望)に照らして「これでいい」と思えるまでの調整を、毎日自分で引き受けているから**(仮説。第4版で言葉にした)。ピクモグはその調整を、少ないやり取りで肩代わりする。

### 選びやすさの核(第4版、2026-09-22)

献立を選ぶとき、人は2つの判断を行き来している。

| | レシピサイト | ピクモグ |
| --- | --- | --- |
| ① 食べたいか(気分) | 人がやる | 人がやる。絵を見て直感で |
| ② 今日作れるか(時間・手間・最近食べた・苦手・材料・家族・疲れ) | **人が1件ずつ確かめる**(開いて、戻って、別のを開く) | **アプリが先に済ませてある** |

疲れるのは②。ピクモグの価値は候補を見せることではなく、**②を肩代わりして、人には①だけを残すこと**。「どれを選んでも今日は大丈夫」な候補だけを出すから、「食べたいか」だけで選べる。

ここから画面の決めごとが出る。
- ②を済ませたことを**見せる**(候補の上に「30分以内・最近食べた料理は後回し の中から」)。見えないと、人は結局自分で確かめる
- カードには②の確認材料を載せすぎない(時間・手間まで)。詳細やレシピを候補の画面に足さない
- 候補は有限。無限に出てくる形は「もっと良いのがあるかも」を生み、レシピサイトと同じ構造に戻る
- ②の中身を太くする機能(家にある食材、家族の希望、疲れた日)が、この核を強くする。新機能はこの表のどこを減らすかで評価する

**判断の軸(機能を足す・変えるときは必ずこれを問う)**: 「この機能で、食事を作る人が考えたり調整したりする仕事は減るか?」 料理数・候補数・入力項目・機能数を増やすこと自体は目的にしない。

| | レシピアプリ | このアプリ |
| --- | --- | --- |
| 目的 | 探して眺める。滞在時間が価値 | 決めて閉じる。速さが価値 |
| 出口 | 保存、閲覧 | 「今日はこれ」と材料メモ。作り方は外部へ |
| 人 | 1人 | 1人でも、同居の二人・家族でも |
| 使い方 | その場で探す | 当日に二択で決める人と、週のはじめにまとめて決めておく人の両方 |
| 収益 | 広告・サブスク | 買い切り(招待する側だけ) |

レシピアプリは強いが、「30秒で決めて閉じる」はあの構造では作りにくい。競合として本当に大きいのは、パートナーへの「なに食べたい?」の連絡と、チャットAIに聞くこと。どちらも候補は出るが決まらない。ここに勝ち筋を置く。

### 成功条件

| 指標 | 目標 |
| --- | --- |
| アプリを開いてから決まるまでの時間(入力を含む) | 中央値 30秒以内 |
| 決定までのタップ数 | 中央値 2タップ以内(条件1 + 選択1)。**第4版で 4 → 2** |
| 決定完了率(決まらずに閉じなかった割合) | 70%以上 |
| 選び直し率(決まった画面で「選び直す」を押した割合) | 30%以下。超えるなら候補の出し方が合っていない |
| 「食べた」記録率(実際に作った・採用した割合) | 40%以上 |
| 二人・家族モードの週あたり利用回数 | 3回以上(TestFlightで20組程度を見る) |

- **タップ数だけで判断しない。** 少ないタップでも見比べに悩めば負担は大きい。時間・選び直し率・「食べた」率と、決めた直後の納得を合わせて見る。

### 続けるかやめるかの判断基準

1. 自己テスト1週間で「決めた直後の納得率」が70%未満なら、決定方式を見直す
2. TestFlight で20組程度の同居カップル・家族に配り、4週後に週3回以上使っている組が半分未満なら、規模を広げない
3. イラストを300枚作るのは 2 を通ったあと

現実的な着地は「数千人がずっと使う小さなアプリ」。大手に勝つ話ではない。

### 設計原則

0. **判断の軸: 作る人が考える・調整する仕事が減るか**(§1)
1. 入力は最大2問。どちらも省略できる。**レシート撮影・食材登録・週の計画・家族の回答は、どれも必須にしない**(使える情報の範囲で決められること)
2. 決定は必ず有限回で終わる。**確認の画面を挟まず、決定は取り消せるようにする**
3. **アプリが学習するのはユーザーの選択だけ**(決定、「どれも違う」、食べた、好み)。「選んだ」「作った」「好き」「今日は気分じゃない」「最近食べた」を同じ意味に混ぜない。**選ばれなかった料理は嫌いと判定しない**
4. 「好き・苦手」(長期の嗜好。ユーザーが付ける)と「今日食べたい」(その日の気分。選択から読む)を別データとして持つ。「今日は違う」は苦手ではない
5. 1品で成立する料理を対等に扱う。主菜+副菜+汁物は前提にしない
6. 決めたあとは材料メモと「レシピを見る」までで手を離す。作り方は持たない
7. 人が増えても「決まる」ことを優先する。全員一致は狙わず、納得できる決め方を用意する
8. AIは通常のロジックで足りるところには使わない

## 2. 決定方式(10件から1つタップ = 決定。いつでも選び直せる + おまかせ)

```
[ホーム]
  「今日の献立を決める」 ─┐
  「疲れた日(おまかせ直行)」┼─→ [気分・時間 1画面(省略可)]
  「今日の予定」(週の献立)─┼─→ そのまま[決まった]へ(選び直させない)
                            │
                            ▼
                  [グリッド] 画面いっぱいに10件。1つタップしたら、その場で決定
                            「どれも違う」で10件を入れ替え(3回目は「おまかせで決める?」)
                            │
                            ▼
                  [決まった] 料理・好み・材料メモ・+1品・レシピを見る・食べた
                            右上「選び直す」→ 同じ10件に戻る(取り消し。学習しない)
```

- **第4版の変更**: 第3版の「選んだ料理を固定して残りを入れ替え、最大3回」と、決定画面の「これにする」を**なくした**。
  - 理由: 「複数ラウンドや再抽選、確認の画面は、本当に負担を減らしているか」という疑問(ユーザーの指摘、2026-09-22)。10件を見比べて1つ選んだ時点で、本人の中では決まっている。そこから確認を重ねるのは、作る人の仕事を増やしているだけ。
  - 代わりに**取り消しを安くする**。決まった画面の右上に常に「選び直す」。押し間違い・材料を見て考え直した、に1タップで戻れる。
  - 最短は 気分(省略可)+ 1タップ。
- **見せ方(2026-09-22 改)**: 10件の2列グリッドをやめ、**1品ずつ大きく見せ、前後の候補がうっすら見える「回転台」**にする。
  - 理由: 実機で「10件だと視線が定まらず選びにくい」(ユーザー)。①だけで選ぶなら、1品に集中できる方が合う。
  - 10品が見えない円周に並び、指で回すと1品ずつ正面に止まる。端がなく一周すると先頭に戻るので、10品で終わることが体で分かる。先頭はいちばん合う料理、隣どうしは系(和洋中エスニック)が続かない。
  - **暫定1位(2026-09-22、ユーザーの指定)**: 気になった料理を上にスワイプ(か正面をタップ)すると「暫定1位」に入る。別の料理を入れると入れ替わる(1 つだけ)。画面下の「〇〇に決める」で暫定1位に決まる。1 品ずつだと横に並べて見比べられないので、「いいな」を覚えておく置き場が要る。「どれも違う」で入れ替えても暫定1位は残る。暫定1位に入れた・入れ替えたは学習しない。
  - ただの横ページングにはしない(ユーザーの指定)。
  - 視差効果を減らす設定では、傾き・回り込みをやめて素直に並べる。
- **件数(10件か、それより少ないか)は未検証**で、自己テストで比べる(§12)。
- 選ばなかった9件は**何も学習しない**(嫌いでも「今日は違う」でもない)。「どれも違う」で外した10件だけが「今日は違う」になる。「選び直す」で取り消した料理も学習しない。
- 決まった画面は、閉じてもホームの「今日決めた料理」から開き直せる(「食べた」を押すまで)。
- カードは絵+料理名+時間の目安+手間。2列×5行で画面に収め、スクロールさせない。
- 主な材料は決まった画面に出す(「冷蔵庫にあるか、買いに行くか」はここで判断し、合わなければ選び直す)。
- おまかせ(ルーレット)は**止まった料理でそのまま決定**。演出は最長1.5秒でタップで止まる。取り消すと1回だけ回し直し、それ以降はグリッドへ。完全な抽選であって「推薦」ではないので、理由は表示しない。

### 2.0 データがたまったあとの入口(v1.x で検討。未実装)

- 使うほど「比べる必要」が減っていくのが理想。初日は少ない比較で決まり、履歴がたまったら**1案を先頭に出して「これにする / ちょっと変えたい」**に進める案がある(Codex 案 §8〜10)。
- ただし**初回は好みの蓄積がないので、1案は運になる**。「無理なく作れるか」(時間・手間・食材)は初回から絞れるが、「今日それを食べたいか」は本人が見ないと分からない。→ 当面は 10件グリッドのまま。切り替えの条件(何回決めたら、選び直し率がいくつなら)は自己テストのデータで決める。
- 「ちょっと変えたい」の理由(もっとラクに / 気分じゃない / 材料がない / 最近食べた / 全部変えて)で**合っていた条件を残して**差し替える案も同じ扱い。毎回理由を答えさせない(「全部変えて」で進める)。提案の理由は、アプリが実際に知っていること(時間・手間・最近食べた)だけを書く。

### 2.1 副菜・汁物の扱い(決め: メイン1品で成立。「+1品」は提案だけ)

「今日なに食べよう」の悩みの大半は主菜で、味噌汁やサラダは習慣で出る。副菜を選ばせると タップ数が倍になり、組み合わせを気にし始めてレシピアプリの土俵に戻る。そこで副菜は**選ばせず、決まったあとに添えるだけ**にする。

| メインの形 | 「+1品あると」に出すもの |
| --- | --- |
| 主菜 | 汁物1件 + 副菜1件(どちらも10分以内) |
| 丼・麺・ワンプレート | 1件だけ(丼・中華系 → 汁物、パスタ・洋食系 → サラダ) |
| 鍋 | 出さない |

- 「決まった」画面のメインの下に小さく出す。タップすると材料名が材料メモに足されるだけ。無視しても何も起きない。
- 直近7日に食べた副菜は避ける。除外食材は同じようにかける。副菜の学習は持たない。
- 週の献立、家族の投票、おまかせでは副菜を対象にしない。あくまでメインの付属。
- 副菜・汁物のデータは20件で足りる。増やすなら「10分以内の定番」に絞って30件程度まで。

### 2.2 献立作成モード(1週間おまかせ)

二択さえ面倒な人、毎日決めたくない人のための入口。**選ばせず、見せて直させる。**

```
[ホーム]「1週間ぶん作る」
  → 曜日ごとに1品ずつ、7枚のカードが並ぶ(月〜日)
  → 気に入らない日は「別の料理に」を1タップ(その日だけ再抽選)
  → 「この献立にする」
  → 週の買い物リスト(材料名をまとめたもの)ができる
  → 当日: ホームに「今日の予定: 生姜焼き」。「これでいく」or「変えたい(二択で決め直す)」
```

- 作り方は§4のスコアを7回使うだけ。加えて週の制約をかける: 同じ系(和・洋・中・エスニック)が2日続かない、1品完結は週3日まで、同じ主材料(豚・鶏・魚など)が2日続かない。
- 曜日ごとの時間の既定値: 平日は「ふつう」、土日は「こだわらない」。設定で変更できる。
- 「別の料理に」は回数制限なし。1タップで入れ替わるだけなので、無限探索にはならない。
- 週の途中で「今日は違う」と思ったら、その日だけ二択で決め直せる。計画派と当日派の両方が同じアプリで成立する。
- 週の献立は履歴に「予定」として入り、当日の「食べた」で確定する。食べなかった日は履歴に残らない。
- 1人モードでも使える。無料。
- **余白の日(第4版)**: 7日すべてを埋めない選択肢を付ける。「5日だけ作る(2日は外食・残り物・変更用)」のように、曜日ごとに「この日は作らない」を1タップで切り替える。予定が崩れる前提で組む。
- **予定の変更(第4版)**: 当日のホームで「作った(食べた)」「今日は変える」「今日は作らない」。「今日は作らない」の料理は、週の残りの空いている日か「余白の日」に回す候補として残す(傷みやすい食材の料理を無条件に後ろへずらさない。保存状態はアプリに分からないので、回すかは本人が決める)。
- 買い物リストは**材料名だけ**をまとめる(第3版から変えない)。分量の合算・家にある量の差し引き・販売単位は持たない(§14)。

## 3. 条件入力(質問は2つ、どちらも省略可)

| 問い | 選択肢 | 既定値 |
| --- | --- | --- |
| 気分 | がっつり / さっぱり / あたたまる / 麺・丼で済ませる / なんでも | なんでも |
| 時間 | すぐ(〜15分) / ふつう(〜30分) / こだわらない | 設定の「標準」(初期値ふつう) |

- 「疲れた日」ボタンはホームに常設。「すぐ・1品完結・手間1」に固定して二択を飛ばしおまかせに直行。
- 設定側: 標準の時間、苦手・食べられない食材、予算目安、出さない料理。人数の設定はなくなった(分量を持たないため)。

## 4. 候補選定ロジック(AI不要)

1. **フィルタ**: 除外食材、出さない料理、時間の上限(15 / 30 / なし)、「麺・丼」は1品完結のみ
2. **スコア**: 気分一致 +3、好み(好き +4 / 苦手 −6)、食べた回数 ×0.5(上限+2)、直近7日 −5、直近14日 −2、今日は違う −4(当日のみ)、過去30日の今日は違う −0.3/回(上限−1.5、減衰)、季節 +1、乱数 0〜1.5
3. **多様性**: 二択の3枚は系(和・洋・中・エスニック)と形態(1品完結/主菜)が重ならないように選ぶ
4. **候補不足時の緩和**: 3件未満なら時間を1段階広げる → それでも3件未満なら気分を外す → それでもなら除外条件を満たす全候補からおまかせ。150件のデータでは大豆(醤油)除外のときだけ緩和が起きる(`meal-decision-dish-list.md` §2)

### 学習するもの(ユーザーの選択のみ)

| 学ぶもの | 元になる操作 | 効き方 |
| --- | --- | --- |
| 今日は違う | 「どれも違う」で外した10件 | その日だけ強く下げる。長期はごく弱く、減衰して消える |
| 食べた回数 | 食べた(=実際に作った・採用した) | 長期にゆるく上げる |
| 最近食べた | 食べた | 7〜14日は下げる |
| 出さない料理 | 明示的な操作 | フィルタで除外 |

- **学習しないもの**: グリッドで選ばれなかった9件、「選び直す」で取り消した料理。唐揚げが好きでも、今日は揚げ物をしたくない日がある。
- 将来役立ちそうなもの(記録だけ先に持つ候補。入力を増やすための学習にはしない): 疲れた日に採用した料理、同じ料理を再び選ぶまでの間隔、「ちょっと変えたい」の理由、家族の希望と実際の採用結果。

### 料理の好み(手動で付ける)

学習とは別に、ユーザーが料理ごとに**好み**を直接付けられる。「好き / ふつう / 苦手 / 出さない」の4段階。「決まった」画面と設定の「料理の好み」(一覧、料理名で絞り込み)から変えられる。

- 好き: +4。よく出る。「お気に入り」はこれに統合し、別のハートは持たない
- 苦手: −6。候補がよほど少ないとき以外は出ない。「嫌い」ではなく「自分からは選ばない」の意味で、除外はしない
- 出さない: フィルタで除外
- 学習が効くまで待てない人と、「苦手な料理が毎回出る」「好きな料理が出ない」への直接の答え。学習(食べた・今日は違う)はこの上に乗る

## 5. ふたり・家族モード(グループ、非同期)

### 考え方

カレンダー共有アプリと同じで、一度グループを作ればずっとつながる。同居のカップル・夫婦・家族が対象。**リアルタイムではない**。先に開いた人が選び、他の人は好きなときに答え、揃った時点で結果が出る。

データは最初から「グループ(2〜6人)」として設計し、v1.1 では画面上2人に限定、v1.2 で人数を開放する。二人を特別扱いしないことで、家族対応が作り直しにならない。

### メンバーの種類

| 種類 | 説明 |
| --- | --- |
| 端末あり | 自分のiPhoneにアプリを入れて招待を受ける |
| 端末なし(代理) | 子どもなど。名前だけ登録し、保護者の端末で「〇〇ちゃんの番」として順番に答える。苦手食材は本人分を登録できる |
| 作る人 | その日に料理する人。メンバーの誰かに毎日つく(既定は前回と同じ人)。最終決定権と「疲れた」合図を持つ |

### 日々の流れ

```
[初回] 作る人が「家族で使う」→ 招待リンクを送る / 端末なしメンバーを追加 → グループ成立

[日々]
  誰か: 気分を選ぶ → 10件から選んで絞る(端末なしメンバーがいれば続けて代理回答)
       ↓ 通知「〇〇さんが今日の候補を選びました」
  他の人: 同じ10件の組で同じように選ぶ
       ↓ 全員揃う、または締め切り(既定18時)
  集計 → 全員の画面に「今日はこれ」
```

- その日の候補(最初の10件と入れ替え用の20件)は最初に答えた人の端末で選定し、共有スペースに置く。全員が同じ組を見る。
- 他の人の選択は見せない。
- 除外食材は全メンバーぶんを合わせてかける。重複回避はグループの共有履歴で働く。
- 締め切りまでに答えなかった人は抜きで集計する。作る人が答えていなければ、作る人に「決めてください」と促す。

### 待っている間にできること(ホームと「回答待ち」画面)

| ボタン | 誰が押せる | 何が起きる |
| --- | --- | --- |
| 催促する | 誰でも | まだ選んでいない人に「今日の希望を選んでね」のプッシュ通知。同じ人には1時間に1回まで |
| 代わりに選ぶ | 端末なしメンバーの保護者 | その子の番として10件グリッドを回し、代理で回答する |
| みんなの希望を見る | **自分が選んだあとだけ** | それぞれの1番(と途中で候補にした料理)、合計点の上位を見る。先に見ると引っ張られるので、選ぶ前は見せない |
| 今そろっている希望で決める | 作る人 | 締め切り前でも、答えた人の分だけで集計して最終決定に進む |
| ひとりで決める | 誰でも | 誰も答えていないとき、1人モードの流れで決める |

- ホームには家族の状況(誰が選択済みか)を常に出し、未回答の人の横に「催促する」または「代わりに選ぶ」を置く。

### 決め方(人数が増えても決まる)

二人のときの「一致したものから選ぶ」は、人数が増えると一致がなくなる。全員に共通する仕組みとして**得点制**にする。

1. 各自の選択から料理に点をつける(最終的に選んだ料理: 3点、途中で「いまの候補」になった料理: 1点)
2. 誰かが「どちらも違う」で外した料理は、その人の拒否として −2点
3. 合計点の上位2品を**作る人**に見せる。「どっち?」で最終決定(作る人優先ルール)
4. 上位が同点で作る人も決められないときはコイントス
5. 二人のときは「一致した料理があればそれを優先して上位2品に入れる」ので、第2版の二人の流れと同じ体験になる

### 判断の優先順位(第4版)

1. 食べられないもの(全員ぶんの除外食材)を守る
2. **作る人が設定した負担の範囲**(時間・手間・「今日は疲れた」)を守る
3. その範囲の中で、家族の希望を加味する(得点制)

- **多数決で作る人の負担を上書きしない。** 家族の人気が高くても、作る人の「すぐ・1品」の範囲外なら上位2品に入れない。
- 家族から希望が届かない日も決められる(締め切り・「ひとりで決める」は第3版どおり)。

### 希望の時期(第4版)

- 家族は希望に「今日食べたい / 今週どこかで」を付けられる。
- 今日採用されなかった希望は**今週の候補に残り**、「1週間ぶん作る」や翌日以降のグリッドで優先して出る。
- 「却下された」と強調する通知は出さない。家族には決まった献立を共有するだけ。

### 歩み寄り(上位2品を誰も選びたくないとき)

- 「今日は譲る」「コイントス」「両方作る(主菜+副菜の組み合わせなら)」の3択
- 「譲った」記録を持ち、次回は譲った人の案から先に見せる
- 相手の選択を変えさせる導線は置かない

### 週の献立の共有とリクエスト

作る人が「1週間ぶん作る」(§2.2)で作った献立はグループ全員に共有される。全員がホームで今週の7日を見られる。

```
メンバー: 木曜のカードに「変えたい」
  → 理由を1タップ(最近食べた / 気分じゃない / これが食べたい)
  → 「これが食べたい」なら、その日の条件で出た3候補から1つ選んで添える
  → 作る人に通知「〇〇さんが木曜を変えたいそうです」
作る人: 「変える」(提案があればそれに、なければ再抽選) / 「そのまま」
  → 結果がメンバーに通知される
```

- リクエストは「変えろ」ではなく「変えたい」。決めるのは作る人のまま。作る人優先ルールを崩さない。
- 1人あたり週2回まで。何度も出せると献立の押し付け合いになる。
- 「これが食べたい」の候補は、その日の条件と除外食材を満たすものから出るので、作る人はそのまま採用できる。
- 献立の変更は買い物リストにも反映される(材料名の差し替え)。
- 家族の子ども(端末なしメンバー)のリクエストは、保護者が代理で出す。

### つながっているとできること

- 今週の献立の共有(上記)
- 買い物リスト(材料メモ)の共有。片方がチェックすれば全員に反映
- 食べた履歴の共有
- 「今日は疲れた」を作る人が1タップで送る。その日の候補が「すぐ・1品」に絞られる
- 「今日は私が作る」で作る人を切り替える

### データの置き場所(Supabase)

| 置き場所 | データ |
| --- | --- |
| Supabase(グループ機能を使うときだけ) | グループ、メンバー(端末あり/なし)、作る人、その日の6枚と各自の回答、決まった料理、今週の献立とリクエスト、共有の買い物リスト、共有の履歴、合図 |
| 端末内 | 1人モードの履歴・お気に入り・今日は違う・苦手食材・設定、料理データ本体(同梱) |

- ログインは「Appleでサインイン」。メールアドレスを預からず、機種変更でもグループが切れない。
- 通知は Edge Function から Apple のプッシュ通知へ。Row Level Security でグループの中の人だけが読める。
- プライバシーポリシーに「グループ機能を使う場合、上記のデータを Supabase に送る」と明記し、1人モードは端末内のみと書き分ける。
- Supabase の契約を止めるとグループ機能が動かなくなる。契約を見直すときは事前に移行先を決める。

### 要判断

- 各自が見る件数(10件×最大3回を推奨)
- 締め切りの既定値(18時推奨)
- 子ども向けのタグ(「子どもも食べやすい」)を料理データに足すか。v1.2 で検討

## 6. 料理データ(決めるためのデータだけ、初回150件)

### 方針

- アプリが持つのは**決めるためのデータだけ**: 料理名、イラスト、気分タグ、時間の目安、手間、費用目安、除外用の食材タグ、主な材料名(3〜5個、分量なし)。
- **分量と手順は持たない。** 「レシピを見る」ボタンで、料理名を使って端末のブラウザに検索を開く。設定でユーザーが普段使うレシピサイトを選べるようにする(既定は一般の検索)。コンテンツを取り込まないので権利問題が起きない。
- 料理名・材料名・イラストはすべて自分で用意した一次データ。外部サイトの転載・スクレイピングはしない。
- 1件あたりの制作は、AIで下書き→机上で確認が約5分、イラスト生成が約5分。150件で約25時間。300件にしても現実的。
- 試作は不要。時間の目安は3段階に丸めて使うので、机上の常識で足りる。

### 自分のレシピメモ(ユーザー自身の記録)

アプリはレシピを配らないが、ユーザーが**自分のレシピの記録**を料理ごとに残せる。メモ(自由文)と参考にしたページのURL。同梱料理にもマイ料理にも付けられる。

- 「決まった」画面に「自分のレシピメモ」欄。書いてあればそこに出る。
- URLを保存してあれば「レシピを見る」はそのページを開く。無ければ検索を開く。
- 1人モードでは端末内のみ。グループ共有は v1.2 で判断。

### レシピの検索先

「レシピを見る」は、料理名を入れた状態で検索結果を開く。検索先は設定で選ぶ: Google(既定、「料理名 レシピ」で検索) / クックパッド / クラシル / DELISH KITCHEN / 楽天レシピ。各サイトの検索URLに料理名を渡すだけで、内容は取り込まない。

### マイ料理(ユーザーが自分の料理を登録する)

「うちの定番」「ここにない料理」を、**写真・料理名・時間の目安**だけで登録できる。登録した料理は同梱の料理と同じ候補に出て、同じように学習される。

| 項目 | 必須 | 既定値 |
| --- | --- | --- |
| 料理名 | 必須 | |
| 写真 | 任意 | 無ければ料理名だけのカード |
| 時間の目安(10 / 15 / 20 / 30 / 40) | 任意 | 20分 |
| 形(主菜 / 1品で完結) | 任意 | 主菜 |
| 気分タグ | 任意 | なし(「なんでも」のときだけ出る。付けると気分絞り込みでも出る) |
| 主な材料 | 任意 | なし(材料メモに出したいときだけ) |
| 除外用の食材タグ | 任意 | なし |

- 登録は30秒で終わる形にする。必須は料理名だけ。
- 写真は端末で長辺640pxに縮小して保存。1人モードでは端末内のみ。
- グループでは、メンバーの誰かのマイ料理も候補に出せる必要がある。写真は Supabase Storage、メタデータは `custom_dishes` テーブルに置く(スキーマ設計を参照)。
- 「食べた」時に撮った写真で同梱料理の表紙を差し替える機能は、マイ料理の写真と同じ仕組みで扱う。
- 手間は時間から自動で付ける(15分以内: 1、30分以内: 2、それ以上: 3)。費用は「普通」。
- 無料は10件まで、Pro は無制限。10件あれば「うちの定番」は入り、それ以上登録したくなった人は Pro を買う理由ができる。

### 収録数と構成(v1.0、検証済み)

| 形態 | 件数 | 例 |
| --- | --- | --- |
| 1品完結(丼・麺・ワンプレート・鍋) | 65 | 親子丼、焼きうどん、ナポリタン、カレー、水炊き、ガパオライス |
| 主菜 | 65 | 生姜焼き、照り焼き、麻婆豆腐、鮭のムニエル、ハンバーグ |
| 副菜・汁物(「+1品」提案用) | 20 | 味噌汁、おひたし、ナムル、卵スープ |

- 無料68 / Pro82。気分5×時間3×除外食材14×料金区分2の420通りで、除外なしの全組み合わせで14件以上残ることを確認済み。
- リストと検証結果は `meal-decision-dish-list.md`、元表は `meal-decision-dishes.csv`。

### 画像

- v1.0は統一スタイルのイラストを画像生成で揃える(商用利用条件を確認)。150枚同一のプロンプト型。
- ユーザーが「食べた」時に撮った写真を、その料理の表紙に差し替えられる(端末内のみ)。
- 300枚への拡張は、続けるかやめるかの判断(§1)を通ったあと。

## 7. AIの使いどころ

| 領域 | 判定 |
| --- | --- |
| 候補の選定・順位付け・学習・集計 | 通常ロジック。説明可能で費用ゼロ |
| 料理データの下書き(開発時) | AIを補助に使う。ユーザーには届かない |
| イラスト(開発時) | 画像生成。商用利用条件を確認 |
| 自由入力の気分 | v2以降、端末内モデルで検討 |
| 冷蔵庫の残り物から提案 | 保留。家にある食材の軽い記録(§14)を入れるなら通常ロジックで足りる |
| レシートの読み取り | v2 以降の候補。入れるなら端末内の文字認識(Vision)。サーバーに送らない |

v1.0の実行時AI利用はゼロ。

## 12. 判断の記録と、残っている要判断

### 決まったこと(第3版まで)

## 14. 改善案の採否(第4版、2026-09-22)

Codex との検討メモ「ピクモグ|今回のセッション共有・仕様検討メモ」を、判断の軸(§1)と既存の決めごとに照らして仕分けた。

### v1.0 に採用(実装済み)

| 案 | 採用した形 | 理由 |
| --- | --- | --- |
| 第二ラウンドをなくす。「これにする」で即決定、確認を挟まず取り消し可能に | グリッドで1タップ = 決定。決まった画面の右上に「選び直す」(§2) | タップ数と確認の手間が減る。取り消しが安ければ確認は要らない |
| 選ばれなかった料理を嫌いと判定しない | 選ばなかった9件・取り消した料理は学習しない(§4) | 3案から1つ選んでも残りが嫌いとは限らない |
| 「選んだ」と「作った」を分ける | 食べた回数は「食べた」だけから数える(§4) | 選んでも作らない日がある |
| ルーレットで待たせない | 最長1.5秒、タップで止まる、止まったら即決定(§2) | 演出で決定を遅らせない |
| 週の献立がある日は選び直させない | 「今日の予定」から開くと、そのまま決まった画面(§2) | 決めた献立を毎日決め直させない |
| 判断の軸・指標 | §1 に判断の軸、成功条件に選び直し率・決定完了率、「タップ数だけで判断しない」 | 機能を足すときの基準がなかった |

### 仕様に書いて、後の版に回す

| 案 | 回す先 | 理由 |
| --- | --- | --- |
| 1案提案 + 部分修正(「もっとラクに」等) | v1.x(§2.0) | 初回は好みがたまっておらず1案は運。自己テストで選び直し率を見てから |
| 初回は3案など少数を表示 | 自己テスト(§12 要判断4) | 件数の最適は未検証。10件は料理の絵で見比べる価値がある |
| 週の献立に「余白の日」、予定変更(今日は作らない → 後日に回す) | v1.0 の後半(§2.2) | 予定が崩れる前提で組める。実装は小さい |
| 家族の優先順位(条件 → 作る人の負担 → 希望)、多数決で上書きしない | v1.1(§5) | 作る人優先ルールの具体化 |
| 希望の時期(今日 / 今週どこかで)、未採用の希望を今週の候補に残す | v1.1(§5) | 家族の希望は初期の好みデータ不足も補う |
| 家にある食材の軽い記録(「ありそう」程度)、「料理に使う / そのまま食べる / 取っておく」 | v2 候補 | 「生姜焼き + 家にあるキムチ」は良い案だが、在庫の更新忘れが負担になる。入れるなら「作った」後にまとめて更新、選んだ時点では消さない |
| レシートから食材を登録 | v2 候補(端末内の文字認識) | レシートは購入記録で在庫ではない(略称・分量不明・開封状態不明)。修正の負担が許容できるか要検証。任意の機能にする |

### 採らない(理由つき)

| 案 | 理由 |
| --- | --- |
| 食材の分量・グラム単位の在庫管理、必要量の合算と差し引き、販売単位の計算 | 「分量を持たない」(第3版の方針)と衝突する。毎回グラムを入れさせると、判断の軸に反して作る人の仕事が増える |
| 提案理由に「買い足しなし」などを出す | 在庫を正確には知らないので断定できない。理由はアプリが実際に知っていることだけ |
