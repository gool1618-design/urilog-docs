# 献立決定アプリ(仮) 企画・仕様たたき台

- 対象: iPhone(iOS 17以降を想定)
- 状態: 企画段階の第1版。「決め」と書いた項目は提案。「要判断」は開発者が決める項目。
- 前提: 個人開発。運用負担と継続費用を最小にする。外部サービスの写真・レシピは取得・転載しない。

---

## 1. コンセプトと成功条件

**「今日なに食べよう?」を、30秒・3タップで「これにする」に変えるアプリ。**

料理を探し続けるアプリではなく、決めるアプリ。決まったあとに材料と作り方を確認でき、買い物にもつながる。

### 成功条件(v1.0で計測する指標)

| 指標 | 目標 |
| --- | --- |
| アプリを開いてから「これにする」までの時間 | 中央値 30秒以内 |
| 決定までのタップ数 | 中央値 4タップ以内(条件1 + 二択2 + 決定1) |
| 決定完了率(開いた回数のうち決まった割合) | 70%以上 |
| 「食べた」記録率(決定のうち実際に食べたと記録された割合) | 40%以上 |

指標は端末内で集計し、任意の匿名送信のみ(バイヤーノートと同じ方針)。

### 設計原則

1. 入力は最大2問。どちらも省略できる。
2. 決定は必ず有限回で終わる。無限スワイプにしない。
3. 「好き」(長期の嗜好)と「今日食べたい」(その日の気分)を別データとして持つ。
4. 「今日は違う」は嫌いではない。その日の順位だけ下げる。
5. 1品で成立する料理(丼・麺・ワンプレート)を対等に扱う。主菜+副菜+汁物は前提にしない。
6. 1人分を基準に材料を持ち、人数は倍率で表示する。
7. AIは、通常のロジックで足りるところには使わない。

## 2. 決定方式の比較と推奨

### 候補の比較

| 方式 | 良い点 | 悪い点 | 判定 |
| --- | --- | --- | --- |
| スワイプ(1枚ずつ 食べたい/違う) | 楽しい。直感的 | 「食べたい」が溜まるだけで決まらない。枚数が読めない。スキップが嫌いと混ざりやすい | 主方式にしない |
| 二択(どっち?) | 1回の判断が軽い。相対比較なので必ず片方が選ばれる。回数が固定で終わりが見える | 1回に見せられる料理が2つ | **主方式に採用** |
| 3〜4枚から1つ選ぶ | 1タップで決まる | 疲れている日は比較対象が多いと選べない。1枚も刺さらない時の逃げ道が要る | 代替案として残す(A/Bテスト候補) |
| ルーレット | 操作ゼロ。楽しい | 選んだ感がなく納得しにくい | **「おまかせ」として補助採用** |

### 決め: 「勝ち抜き二択」+「おまかせ」

```
[ホーム]
  「今日の献立を決める」 ─┐
  「疲れた日(おまかせ直行)」┼─→ [気分 1タップ(省略可)]
                            │
                            ▼
                  [どっち? 1回目]  A vs B  → 勝者
                  [どっち? 2回目]  勝者 vs C → 今日の料理
                            │
                            ▼
                  [決定画面] 「これにする」 / 「別の候補を見る」(最大2回) / 「おまかせで決める」
                            │
                            ▼
                  [料理詳細] 材料(人数切替)・作り方・買い物リストに追加・食べた記録
```

- 二択は2回で終わる。見る料理は3つ。タップは2回。
- 二択で選ばれなかった料理は「今日は違う」信号だけを受け取る(§6)。
- 「別の候補を見る」は2回まで。3回目は自動的に「おまかせ」を提案する。ここで無限探索を断つ。
- 「おまかせ」は、今回のセッションで見た料理も含めた候補上位からルーレット演出で1つ決める。演出は2秒以内、スキップ可。
- 二択の見せ方は写真+料理名+調理時間の大きな2枚カード。左右タップまたは上下タップ。

### 二人モードでも同じ操作にする理由

二択はそのまま「2人が同じ問いに答える」形に拡張できる(§5)。1人用と2人用で操作を覚え直させない。

### 要判断

- 二択の回数を2回固定にするか、「もう1回だけ比べる」を許すか。推奨は2回固定。
- 代替案「3枚から1つ」を試験実装して、TestFlightで比較するか。

## 3. 条件入力をどこまで減らすか

### 決め: 質問は「気分」と「時間」の2つだけ。どちらも省略可

| 問い | 選択肢 | 既定値 |
| --- | --- | --- |
| 気分 | がっつり / さっぱり / あたたまる / 麺・丼で済ませる / なんでも | 前回の選択ではなく「なんでも」 |
| 時間 | 10分 / 20分 / 40分以上OK / いつも通り | 設定の「標準の調理時間」(初期値20分) |

- 画面は1枚。気分チップ5個と時間チップ4個。何も触らず「候補を見る」でも進める。
- 「疲れた日」ボタンはホームに常設。押すと「15分以内・1品完結・手間レベル1」で二択を飛ばしておまかせに直行。
- 予算・手間・人数は設定側に持ち、毎回は聞かない。
- 時間帯で用途を推定しない(昼にも夕食を決める人がいる)。代わりに「昼ごはん向き」タグを候補の多様性に使うだけにする。

### 設定側に置く条件(初回オンボーディングで1画面、あとから変更可)

- 人数(1〜4、初期値1)
- 標準の調理時間(10 / 20 / 40分)
- 苦手・食べられない食材(食材タグから選択。アレルゲン主要8品目+よくある苦手食材20程度)
- 予算目安(節約 / 普通 / 気にしない)
- 出さない料理(料理単位。決定画面の「…」から追加)

## 4. 候補選定ロジック(AI不要)

### 手順

1. **フィルタ(絶対条件)**
   - 苦手・除外食材を含む料理を除く
   - 「出さない料理」を除く
   - 調理時間が選択時間を超える料理を除く(「いつも通り」は標準時間+10分まで許容)
   - 気分「麺・丼で済ませる」のときは1品完結のみ
2. **スコア(相対順位)**
   - 気分タグ一致: +3
   - お気に入り: +2、過去の「食べた」回数: 回数×0.5(上限+2)
   - 直近7日に食べた: −5、直近14日: −2
   - 今日のセッションで「今日は違う」になった: −4(セッション内のみ)
   - 過去30日の「今日は違う」累積: 1回あたり−0.3(上限−1.5)。指数減衰で消える。嫌い扱いにはしない
   - 季節タグ一致: +1
   - 乱数: 0〜1.5(毎回同じ並びにならないため)
3. **多様性の確保**
   - 二択の3枚は「主カテゴリ(和・洋・中・エスニック)」と「形態(1品完結 / 主菜)」が重ならないように上位から選ぶ
4. **候補不足時**
   - フィルタ後が3件未満なら、時間条件を1段階緩めて再検索し、画面に「40分の料理も含めました」と1行表示

### 「好き」と「今日食べたい」の分離

| データ | 意味 | 更新のきっかけ | 使い方 |
| --- | --- | --- | --- |
| お気に入り | 長期的に好き | 料理詳細のハート | スコアに弱く加点。候補から消えない |
| 食べた履歴 | 実際に食べた事実 | 決定後の「食べた」 | 直近は減点(重複回避)、長期は加点(好みの推定) |
| 今日は違う | その日の気分に合わない | 二択で選ばれなかった | その日だけ強く減点。長期はごく弱く減点し減衰 |
| 出さない料理 | 明示的な除外 | ユーザーが操作 | フィルタで除外 |

## 5. 二人モード

### 前提

1人モードを基本とし、二人モードは追加機能。v1.0には入れず、v1.1以降で段階的に入れる(§9)。

### 決め: まず「端末を渡す」方式(サーバー不要)

```
[二人で決める] をタップ
  → 人数2で候補6枚を選定
  → Aさん: 二択を3回(6枚を3組)     → Aの「今日食べたい」3枚
  → 「Bさんに渡してください」画面
  → Bさん: 同じ3組の二択            → Bの「今日食べたい」3枚
  → 一致判定
```

- 同じ端末で順番に答えるので、通信・アカウント・サーバーが要らない。カップル・夫婦の同居利用ならこれで十分成立する。
- Bには Aの選択を見せない(先に見ると引っ張られる)。
- 別々の端末で遠隔に選ぶ方式は v1.2 以降。CloudKit共有(Appleの無料枠)または6桁の合言葉で結ぶ短命セッションを検討。自前サーバーは最後の手段。

### 一致しなかった場合の流れ(重要)

| 一致数 | 流れ |
| --- | --- |
| 2〜3枚一致 | 一致した料理どうしで二択1回 → 決定 |
| 1枚一致 | その料理を提示。「これにする」/「他の案も見る」 |
| 0枚一致 | 下記の「歩み寄り」へ |

**歩み寄り(0枚一致)**

1. Aの1位とBの1位を並べて表示し、3つのボタンを出す。
   - **「今日は譲る」**(Aが押せばBの1位、Bが押せばAの1位に決定)
   - **「コイントス」**(演出付きで1つに決める)
   - **「両方作る」**(主菜+副菜として両立できる組み合わせなら提案。1品完結どうしなら出さない)
2. 「譲った」記録を端末内に持ち、次回0枚一致のときは「前回はAさんが譲ったので、今日はAさんの案から」と先に表示する。公平感を演出で担保する。
3. さらに解決しない場合は、二人の「今日は違う」を除いた残り全候補からおまかせ。

ここは押し付けが起きやすい場面なので、「相手の選択を変えさせる」導線は置かない。

### 要判断

- 二人モードで各自が見る枚数を6枚(二択3回)にするか、4枚(二択2回)にするか。一致率を上げるには6枚が必要。
- 遠隔方式をやるか、v1.xでは同居利用に絞るか。

## 6. 料理データ(写真・レシピ・調理時間)の用意の仕方

これが個人開発で最も工数がかかる部分。方針を先に固定する。

### 方針

- 料理名・材料・手順・写真はすべて**自分で用意した一次データ**とする。外部サイトの転載・スクレイピングはしない。
- 一般に、料理の材料や手順という「アイデア・事実」自体は著作権の対象になりにくいが、レシピの文章表現や写真は保護される。自分の言葉で短く書き、写真も自前にすることでこの問題を避ける。
- 作り方は「要点3〜5行」に絞る。本格レシピはこのアプリの役割ではない。詳しく知りたい人向けに「この料理名でレシピを検索」ボタン(端末の既定ブラウザで検索を開くだけ)を置く。コンテンツを取り込まないので権利問題が起きない。

### 収録数と構成(v1.0)

| 形態 | 目安件数 | 例 |
| --- | --- | --- |
| 1品完結(丼・麺・ワンプレート・鍋) | 35 | 親子丼、豚キムチ丼、焼きうどん、ナポリタン、鶏鍋 |
| 主菜(単品で夕食の中心になるもの) | 35 | 生姜焼き、鶏の照り焼き、麻婆豆腐、鮭のムニエル |
| 副菜・汁物(「+1品」提案用、5〜10分) | 10 | 味噌汁、小松菜のおひたし、トマトサラダ |

- 合計80件。時間×気分×除外食材で絞っても3件以上残る最低ライン。
- 調理時間は10 / 15 / 20 / 30 / 40分の5段階で自分の試作で計測。手間レベルは1〜3。
- 費用目安は1人分の材料費を3段階(節約: 〜200円 / 普通: 〜400円 / 気にしない)。

### 写真

| 案 | 費用 | 運用 | 判定 |
| --- | --- | --- | --- |
| 自分で作って撮る | 材料費のみ | 80品の試作と撮影。時間はかかるが最も自然 | 長期の本命。少しずつ置き換え |
| 統一スタイルのイラスト(画像生成を利用) | 生成サービス費が少額 | 数日で80枚揃う。統一感を出しやすい。商用利用条件の確認が必要 | **v1.0はこれで揃える** |
| 有料ストック写真 | 1枚数百〜数千円 | 80枚で数万円。料理の一致率が低い | 採用しない |
| 写真なし(タイポグラフィ+アイコン) | 0 | 二択の直感性が落ちる | 採用しない |

- v1.0はイラスト調で統一し、ユーザーが「食べた」時に撮った自分の写真をその料理の表紙に差し替えられるようにする(端末内のみ)。自分の写真が増えるほどアプリが自分のものになる。

### データの配信

- v1.0はアプリ内にJSONで同梱。サーバー不要。
- 料理の追加・修正はアプリ更新で配信。将来、静的JSONをCDN(GitHub PagesやCloudflare Pagesなど無料枠)に置いて起動時に差分取得する形に移行できるようにIDとバージョンを持つ。

### データモデル(案)

```json
{
  "id": "oyakodon",
  "name": "親子丼",
  "kana": "おやこどん",
  "form": "one_dish",              // one_dish | main | side | soup
  "cuisine": "japanese",           // japanese | western | chinese | ethnic
  "moodTags": ["hearty", "warm"],  // hearty | light | warm | noodle_rice
  "seasonTags": ["all"],
  "cookTimeMin": 15,
  "effort": 1,                     // 1〜3
  "costLevel": 1,                  // 1〜3
  "servingsBase": 1,
  "ingredients": [
    {"name": "鶏もも肉", "amount": 100, "unit": "g", "scalable": true, "tags": ["chicken"]},
    {"name": "卵", "amount": 2, "unit": "個", "scalable": true, "tags": ["egg"]},
    {"name": "玉ねぎ", "amount": 0.25, "unit": "個", "scalable": true, "tags": []},
    {"name": "めんつゆ(3倍)", "amount": 2, "unit": "大さじ", "scalable": true, "tags": ["soy", "wheat"]},
    {"name": "ごはん", "amount": 1, "unit": "杯", "scalable": true, "tags": []}
  ],
  "steps": [
    "玉ねぎを薄切り、鶏肉を一口大に切る",
    "めんつゆと水100mlを煮立て、玉ねぎと鶏肉を5分煮る",
    "溶き卵を回し入れ、半熟で火を止めてごはんにのせる"
  ],
  "pairSuggestions": ["misoshiru", "komatsuna_ohitashi"],
  "image": "oyakodon",
  "dataVersion": 1
}
```

- 人数換算: `scalable` の材料のみ倍率をかける。大さじ・個は0.5単位に丸める。
- 苦手食材は `ingredients[].tags` で照合する。

## 7. AIが必要な部分と、通常ロジックで足りる部分

| 領域 | 判定 | 理由 |
| --- | --- | --- |
| 候補の選定・順位付け | 通常ロジック | §4のスコアで十分。説明可能で、費用ゼロ |
| 重複回避・除外・人数換算 | 通常ロジック | ルールで完結 |
| 二人の一致判定・歩み寄り | 通常ロジック | 集合演算と固定の流れ |
| 料理データの下書き(開発時) | AIを補助に使う | 材料・手順・タグの下書きを生成し、開発者が試作して確認・修正。ユーザーには届かない使い方 |
| 画像(開発時) | 画像生成を利用 | §6。商用利用条件を確認したうえで使う |
| 自由入力の気分(「なんか辛いのがいい」) | v2以降、端末内モデルで検討 | iOSの端末内基盤モデルが使える機種なら通信費ゼロで気分→タグ変換ができる。非対応機種ではチップ選択にフォールバック |
| 冷蔵庫の残り物から提案 | 保留 | 需要は大きいが、入力の手間と外部API費用が原則に反する。有料機能として検討 |

v1.0の実行時AI利用はゼロ。継続費用もゼロ。

## 8. 画面構成

| 画面 | 役割 | 主な要素 |
| --- | --- | --- |
| ホーム | 入口 | 「今日の献立を決める」(大)、「疲れた日」、前回決めた料理、買い物リストの未購入件数 |
| 気分・時間 | 条件1画面 | 気分チップ5、時間チップ4、「候補を見る」、「スキップ」 |
| どっち? | 二択 | 2枚の大カード(イラスト・料理名・時間)。「どちらも違う」は小さく下部に |
| 決定 | 確定 | 選ばれた料理、「これにする」、「別の候補を見る」(残り回数表示)、「おまかせで決める」 |
| 料理詳細 | 調理支援 | 人数切替、材料、作り方、「+1品」提案、「買い物リストに追加」、「食べた」、ハート、「…」(出さない料理に追加、レシピを検索) |
| 買い物リスト | 買い物 | 料理別にまとめた材料、チェック、手動追加 |
| 履歴・お気に入り | 振り返り | 食べた日付順、お気に入り一覧、自分の写真 |
| 設定 | 条件 | 人数、標準時間、苦手食材、予算、出さない料理、二人モード、データ書き出し |

- タブは「決める / 買い物 / 履歴 / 設定」の4つ。
- 「決める」の流れは常にフルスクリーンで、決まるまでタブを隠す。
- 決定画面の演出は短く(1秒未満)。疲れている日に待たせない。

## 9. リリース計画

### v1.0(最小構成: 1人で、短時間で決まる)

- 1人モードの決定フロー一式(気分・時間、勝ち抜き二択、別候補2回、おまかせ)
- 料理データ80件(イラスト、材料、要点手順、時間、手間、費用)
- フィルタとスコア(苦手食材、出さない料理、直近の重複回避、今日は違う)
- 料理詳細(人数換算、+1品、レシピ検索ボタン)
- 買い物リスト(料理からの追加とチェック)
- 食べた履歴、お気に入り、自分の写真の差し替え
- 設定、オンボーディング1画面
- データは端末内のみ。iCloudバックアップに含まれる
- 任意・匿名の利用統計(指標§1)

### v1.1

- 二人モード「端末を渡す」方式と歩み寄りの流れ
- 料理データ+40件
- 買い物リストの共有(iOS標準の共有シートでテキスト出力)

### v1.2以降(需要を見て)

- 遠隔の二人モード(CloudKit共有 or 合言葉)
- 自由入力の気分(端末内モデル)
- 料理データの差分配信
- 週まとめ買い(数日分を先に決めて買い物リストを合算)

### v1.0に入れないもの(意図的に)

- 本格レシピ、動画、栄養計算
- ユーザー投稿レシピ(審査・権利・運用負担が個人開発に合わない)
- SNS共有機能(決めるアプリに不要)
- 広告

## 10. 収益化

### 決め: 無料+買い切りのProアンロック

| 区分 | 内容 |
| --- | --- |
| 無料 | 1人モードの決定フロー全部。料理40件。履歴30日。買い物リスト |
| Pro(買い切り 800〜1,200円、要判断) | 料理全件(80件+追加パック)、二人モード、履歴無制限、自分の写真差し替え、苦手食材の細かい設定、iCloud同期(将来) |

- 決める体験自体は無料で完結させる。制限で「決まらない」ことが起きないようにする(無料の40件でも§4の3件以上が残るようにデータを選ぶ)。
- サブスクリプションは、月ごとの料理データ追加や実行時AI費用が発生するまで導入しない。個人開発で継続提供の義務を負わない。
- 広告は入れない。疲れた日に開くアプリの体験を壊し、収益も見込めない。
- 追加パック(例: 「鍋20選」「お弁当おかず20選」)は非消耗型アプリ内課金で数百円。データ制作の工数と直接つながるので、続けやすい。

## 11. 技術構成(参考)

- Swift / SwiftUI。iOS 17以上
- 永続化: SwiftData(またはCore Data)。料理データは同梱JSONを初回起動時に取り込み
- 画像: アプリ同梱のアセット(イラスト80枚、1枚200KB以下でアプリ容量を抑える)
- 同期: v1.0はなし。v1.2でCloudKitプライベートDB(無料枠)
- サーバー: なし。運用費ゼロ
- 計測: 端末内集計+任意の匿名送信(送信先は最小限。既存アプリの方針に合わせてプライバシーポリシーに明記)

## 12. 開発者が判断する項目(要判断まとめ)

1. 二択の回数(2回固定を推奨)と、「3枚から1つ」の試験実装をするか
2. 気分チップの語(がっつり / さっぱり / あたたまる / 麺・丼で済ませる / なんでも)で違和感がないか
3. 二人モードの見せ枚数(6枚推奨)と、遠隔方式をやる時期
4. 写真をv1.0でイラスト調に統一することへの納得感
5. 料理80件を自分で試作・計測する工数を確保できるか(1日3〜4品で約1か月)
6. Pro価格帯と無料枠の料理件数
7. アプリ名(このドキュメントでは仮称)
