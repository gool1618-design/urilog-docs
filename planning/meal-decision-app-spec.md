# 献立決定アプリ(仮) 企画・仕様 第2版

- 対象: iPhone(iOS 17以降を想定)
- 状態: 第2版。第1版のたたき台に対する議論(料理データの作り方、レシピ表示、調理時間の扱い、学習対象、二人モードの方式、データの置き場所)を反映した。「決め」は決定事項、「要判断」は開発者が決める項目。
- 前提: 個人開発。運用負担と継続費用を最小にする。外部サービスの写真・レシピは取得・転載しない。Supabase は契約済みのものを使う。

---

## 1. コンセプトと成功条件

**「今日なに食べよう?」を、30秒・3タップで「これにする」に変えるアプリ。**

料理を探し続けるアプリではなく、決めるアプリ。決まったら材料と作り方がすぐ見え、買い物にもつながる。同居の二人なら、一度つなげばずっと二人で使える。

### 成功条件(v1.0で計測する指標)

| 指標 | 目標 |
| --- | --- |
| アプリを開いてから「これにする」までの時間 | 中央値 30秒以内 |
| 決定までのタップ数 | 中央値 4タップ以内(条件1 + 二択2 + 決定1) |
| 決定完了率(開いた回数のうち決まった割合) | 70%以上 |
| 「食べた」記録率(決定のうち実際に食べたと記録された割合) | 40%以上 |

指標は端末内で集計し、任意の匿名送信のみ。

### 設計原則

1. 入力は最大2問。どちらも省略できる。
2. 決定は必ず有限回で終わる。無限スワイプにしない。
3. **アプリが学習するのはユーザーの選択だけ。** 二択の勝敗、決定、食べた、お気に入り。料理の調理時間や手間は料理側の属性であり、学習対象ではない。
4. 「好き」(長期の嗜好)と「今日食べたい」(その日の気分)を別データとして持つ。
5. 「今日は違う」は嫌いではない。その日の順位だけ下げる。
6. 1品で成立する料理(丼・麺・ワンプレート・鍋)を対等に扱う。主菜+副菜+汁物は前提にしない。
7. 1人分を基準に材料を持ち、人数は倍率で表示する。
8. 決めた料理の材料と作り方はアプリ内で見せる。外に出すのは「写真つきの詳しいレシピを探したい人」だけ。
9. AIは、通常のロジックで足りるところには使わない。

## 2. 決定方式(決め: 勝ち抜き二択 + おまかせ)

### 候補の比較

| 方式 | 良い点 | 悪い点 | 判定 |
| --- | --- | --- | --- |
| スワイプ(1枚ずつ 食べたい/違う) | 楽しい。直感的 | 「食べたい」が溜まるだけで決まらない。枚数が読めない。スキップが嫌いと混ざりやすい | 主方式にしない |
| 二択(どっち?) | 1回の判断が軽い。相対比較なので必ず片方が選ばれる。回数が固定で終わりが見える | 1回に見せられる料理が2つ | **主方式** |
| 3〜4枚から1つ選ぶ | 1タップで決まる | 疲れている日は比較対象が多いと選べない | 代替案として残す(自己テストで判断) |
| ルーレット | 操作ゼロ。楽しい | 選んだ感がなく納得しにくい | **「おまかせ」として補助採用** |

### 流れ

```
[ホーム]
  「今日の献立を決める」 ─┐
  「疲れた日(おまかせ直行)」┼─→ [気分・時間 1画面(省略可)]
                            │
                            ▼
                  [どっち? 1回目]  A vs B  → 勝者
                  [どっち? 2回目]  勝者 vs C → 今日の料理
                            │
                            ▼
                  [決定画面] 料理 + 主な材料チップ
                            「これにする」 / 「別の候補を見る」(最大2回) / 「おまかせで決める」
                            │
                            ▼
                  [料理詳細] 材料(人数切替)・作り方・買い物リストに追加・食べた記録
```

- 二択は2回で終わる。見る料理は3つ。タップは2回。カードは写真(イラスト)+料理名+調理時間+手間。
- 二択で選ばれなかった料理は「今日は違う」信号だけを受け取る(§4)。
- 「別の候補を見る」は2回まで。3回目は自動的に「おまかせ」を提案する。
- 「おまかせ」は候補上位からルーレット演出で1つ決める。演出は2秒以内、スキップ可。
- **決定画面には主な材料を名前だけチップで並べる。** 「冷蔵庫にあるか、買いに行くか」を「これにする」の前に判断できるようにするため。分量と手順は料理詳細で見せる。

## 3. 条件入力(決め: 質問は「気分」と「時間」の2つだけ、どちらも省略可)

| 問い | 選択肢 | 既定値 |
| --- | --- | --- |
| 気分 | がっつり / さっぱり / あたたまる / 麺・丼で済ませる / なんでも | 「なんでも」 |
| 時間 | すぐ(〜15分) / ふつう(〜30分) / こだわらない | 設定の「標準」(初期値「ふつう」) |

- 時間は3段階に絞った。分数の精度は要らない。絞り込みの粗さと料理データ側の付けやすさが釣り合う粒度にした。
- 画面は1枚。何も触らず「候補を見る」でも進める。
- 「疲れた日」ボタンはホームに常設。「すぐ・1品完結・手間レベル1」に固定して二択を飛ばしおまかせに直行。
- 予算・人数は設定側に持ち、毎回は聞かない。

### 設定側に置く条件(初回オンボーディングで1画面)

- 人数(1〜4、初期値1)
- 標準の時間(すぐ / ふつう / こだわらない)
- 苦手・食べられない食材(卵・乳・小麦・えび・そば、豚・鶏・牛・魚、豆腐・きのこ・ごま、大豆)
- 予算目安(節約 / 普通 / 気にしない)
- 出さない料理(料理単位。決定画面の「…」から追加)

## 4. 候補選定ロジック(AI不要)

### 手順

1. **フィルタ(絶対条件)**
   - 苦手・除外食材を含む料理、出さない料理を除く
   - 調理時間が選択の上限(15 / 30 / 制限なし)を超える料理を除く
   - 気分「麺・丼で済ませる」のときは1品完結のみ
2. **スコア(相対順位)**
   - 気分タグ一致: +3
   - お気に入り: +2、過去の「食べた」回数: 回数×0.5(上限+2)
   - 直近7日に食べた: −5、直近14日: −2
   - 今日のセッションで「今日は違う」になった: −4(セッション内のみ)
   - 過去30日の「今日は違う」累積: 1回あたり−0.3(上限−1.5)。指数減衰で消える
   - 季節タグ一致: +1
   - 乱数: 0〜1.5
3. **多様性の確保**: 二択の3枚は系(和・洋・中・エスニック)と形態(1品完結/主菜)が重ならないように上位から選ぶ
4. **候補不足時(2段階の緩和)**
   - 緩和1: 3件未満なら時間を1段階広げる(すぐ→ふつう→こだわらない)。「30分の料理も含めました」と1行表示
   - 緩和2: それでも3件未満なら気分の条件を外す。「気分の条件を外して探しました」と1行表示
   - それでも3件未満なら、除外条件を満たす全候補からおまかせに直行
   - 150件のデータでは、3件未満になるのは大豆(醤油)除外のときだけ(`meal-decision-dish-list.md` §2)

### 学習するもの(決め: ユーザーの選択のみ)

| 学ぶもの | 元になる操作 | 効き方 |
| --- | --- | --- |
| 今日は違う | 二択で選ばれなかった | その日だけ強く下げる。長期はごく弱く、減衰して消える |
| 好み | 決定した、食べた、お気に入り | 長期にゆるく上げる。候補から消えない |
| 最近食べた | 食べた | 7〜14日は下げる(重複回避) |
| 出さない料理 | ユーザーが明示的に操作 | フィルタで除外 |

調理時間・手間・費用は料理の属性で、学習しない。ユーザーに「実際は何分かかったか」のような追加入力も求めない。

## 5. 二人モード(決め: ペアリング方式、非同期)

### 考え方

カレンダー共有アプリと同じ「一度ペアにしたら、あとはずっとつながっている」形。同居・同棲のカップル、夫婦が主な利用者。毎回リンクを送ったり端末を渡したりする方式は採らない。

**リアルタイムではない。** 先に開いた人が選び、相手は好きなときに答え、両方揃ったときに結果が出る。揃った瞬間に両方の画面に反映されるので体感はほぼ即時。

### 流れ

```
[初回] Aが「ふたりで使う」→ 招待リンクを送る → Bが受け取る → ペア成立(以後、設定不要)

[日々]
  A: 気分を選ぶ → 6枚の二択を3回答える → 「Bさんの回答を待っています」
       ↓ 通知「Aさんが今日の候補を選びました」
  B: 同じ6枚で二択を3回答える
       ↓
  一致判定 → 二人の画面に「今日はこれ」
```

- その日の6枚は先に答えた人の端末で選定し、共有スペースに置く。二人が同じ6枚を見る。
- Bには Aの選択を見せない(先に見ると引っ張られる)。
- 二人モードのときは、二人の除外食材を両方かける。重複回避は共有の履歴で働く。
- 相手が夕方までに答えなければ「ひとりで決める」に切り替えられる。

### 一致しなかった場合

| 一致数 | 流れ |
| --- | --- |
| 2〜3枚一致 | 一致した料理どうしで二択1回 → 決定 |
| 1枚一致 | その料理を提示。「これにする」/「他の案も見る」 |
| 0枚一致 | 下記の「歩み寄り」へ |

**歩み寄り(0枚一致)**

1. Aの1位とBの1位を並べて表示し、3つのボタンを出す。
   - 「今日は譲る」(押した人の相手の1位に決定)
   - 「コイントス」(演出付きで1つに決める)
   - 「両方作る」(主菜+副菜として両立できる組み合わせなら提案。1品完結どうしなら出さない)
2. 「譲った」記録を持ち、次回0枚一致のときは「前回はAさんが譲ったので、今日はAさんの案から」と先に表示する。
3. さらに解決しない場合は、二人の「今日は違う」を除いた残り全候補からおまかせ。

相手の選択を変えさせる導線は置かない。

### つながっているとできること(v1.1で同時に入れる)

- 買い物リストの共有(片方がチェックすれば相手にも反映)
- 食べた履歴の共有
- 「今日は疲れた」を1タップで相手に伝える。相手側の候補が「すぐ・1品」に絞られる
- 「今日は私が作る」の宣言。作る人の時間設定で絞る

### データの置き場所(決め: Supabase)

| 置き場所 | データ |
| --- | --- |
| Supabase(二人モードを使うときだけ) | ペア、その日の6枚と各自の回答、決まった料理、共有の買い物リスト、共有の食べた履歴、合図(疲れた・私が作る) |
| 端末内 | 1人モードの履歴・お気に入り・今日は違う・苦手食材・設定、料理データ本体(同梱) |

- Supabase は契約済み。二人モードのデータは1ペアあたり数KBで、容量は問題にならない。
- ログインは「Appleでサインイン」。メールアドレスを預からずに済み、機種変更でもペアが切れない。
- 相手が答えたことの通知は、Edge Function から Apple のプッシュ通知に投げる。Supabase の枠内で済む。
- プライバシーポリシーに「二人モードを使う場合、上記のデータを Supabase に送る」と明記する。1人モードは端末内のみと書き分ける。
- CloudKit の共有機能は費用ゼロだが実装が重く、iCloud 未サインインの人が使えないため採らない。

### 要判断

- 各自が見る枚数(6枚推奨。一致率を上げるには6枚必要)
- 相手を待つ締め切りの既定値(18時を推奨)

## 6. 料理データ(決め: 2層方式、初回150件、全件試作はしない)

これが個人開発で最も工数がかかる部分。第1版の「80件を全部試作して時間を計る」は重すぎるので改めた。

### 方針

- 料理名・材料・手順・画像はすべて**自分で用意した一次データ**。外部サイトの転載・スクレイピングはしない。料理の材料や手順という「アイデア・事実」自体は著作権の対象になりにくいが、レシピの文章表現や写真は保護されるため、自分の言葉で短く書き、画像も自前にする。
- **アプリ内で見せるもの**: 1人分の材料(分量つき)、要点手順3〜5行、調理時間の目安、手間、費用目安。決めた料理の作り方がアプリ内で分からないのは不自然なので、ここは省かない。
- **外に任せるもの**: 写真つきの詳しいレシピ。「この料理名でレシピを検索」ボタンで端末のブラウザに検索を開くだけ。コンテンツを取り込まないので権利問題が起きない。

### 2層のデータ

| 層 | 内容 | 作り方 | 1件あたり |
| --- | --- | --- | --- |
| A: 決めるためのデータ | 料理名、イラスト、気分タグ、調理時間(すぐ/ふつう/じっくり相当の目安)、手間、費用、除外用の食材タグ、主な材料名 | AIで下書き → 机上で確認 | 約10分 + イラスト5分 |
| B: 作るためのデータ | 1人分の分量、要点手順3〜5行 | AIで下書き → 机上で確認。家庭料理の定番なら分量の誤りは机上で見つかる | 約10分 |

- 試作は全件ではなく20〜30件に絞る。目的は「時間の目安が全体としてずれていないか」「手順の文体が実用に耐えるか」の確認。
- 初回150件で、A層とB層の両方を揃える。工数の目安は 150 × 25分 ≒ 63時間。以後は月20件ずつ追加。
- 調理時間は 10 / 15 / 20 / 30 / 40 分の目安で持ち、絞り込みでは「すぐ(〜15)/ふつう(〜30)/こだわらない」の3段階に丸めて使う。

### 収録数と構成(v1.0、検証済み)

| 形態 | 件数 | 例 |
| --- | --- | --- |
| 1品完結(丼・麺・ワンプレート・鍋) | 65 | 親子丼、焼きうどん、ナポリタン、カレー、水炊き、ガパオライス |
| 主菜 | 65 | 生姜焼き、照り焼き、麻婆豆腐、鮭のムニエル、ハンバーグ |
| 副菜・汁物(「+1品」提案用) | 20 | 味噌汁、おひたし、ナムル、卵スープ |

- 無料68 / Pro82。気分5×時間3×除外食材14×料金区分2の420通りで、除外なしの全組み合わせで14件以上残ることを確認済み。
- リストと検証結果は `meal-decision-dish-list.md`、元表は `meal-decision-dishes.csv`。

### 画像

| 案 | 費用 | 判定 |
| --- | --- | --- |
| 統一スタイルのイラスト(画像生成を利用) | 生成サービス費が少額 | **v1.0はこれで揃える。** 150枚を同一のプロンプト型で生成。商用利用条件を確認 |
| 自分で作って撮る | 材料費のみ | 試作する20〜30件から差し替えていく |
| 有料ストック写真 | 1枚数百〜数千円 | 採用しない |
| 写真なし | 0 | 二択の直感性が落ちる。採用しない |

- ユーザーが「食べた」時に撮った自分の写真をその料理の表紙に差し替えられるようにする(端末内のみ)。

### データの配信

- 将来は Supabase Storage に静的JSONを置いて起動時に差分取得する形に移行できるよう、IDとバージョンを持つ。

## 7. AIが必要な部分と、通常ロジックで足りる部分

| 領域 | 判定 | 理由 |
| --- | --- | --- |
| 候補の選定・順位付け・学習 | 通常ロジック | §4のスコアで十分。説明可能で、費用ゼロ |
| 重複回避・除外・人数換算 | 通常ロジック | ルールで完結 |
| 二人の一致判定・歩み寄り | 通常ロジック | 集合演算と固定の流れ |
| 料理データの下書き(開発時) | AIを補助に使う | A層・B層の下書きを生成し、開発者が机上で確認。ユーザーには届かない使い方 |
| 画像(開発時) | 画像生成を利用 | §6。商用利用条件を確認したうえで使う |
| 自由入力の気分(「なんか辛いのがいい」) | v2以降、端末内モデルで検討 | 通信費ゼロで気分→タグ変換ができる機種に限る。非対応機種はチップ選択 |
| 冷蔵庫の残り物から提案 | 保留 | 入力の手間と外部API費用が原則に反する |

v1.0の実行時AI利用はゼロ。

## 8. 画面構成

| 画面 | 役割 | 主な要素 |
| --- | --- | --- |
| ホーム | 入口 | 「今日の献立を決める」(大)、「疲れた日」、前回決めた料理、買い物リストの未購入件数。二人モード時は相手の状態(「Bさんの回答待ち」「Bさんが疲れています」) |
| 気分・時間 | 条件1画面 | 気分チップ5、時間チップ3、「候補を見る」、「スキップ」 |
| どっち? | 二択 | 2枚の大カード(イラスト・料理名・時間・手間)。「どちらも違う」は小さく |
| 決定 | 確定 | 選ばれた料理、**主な材料チップ**、「これにする」、「別の候補を見る」(残り回数表示)、「おまかせで決める」 |
| 料理詳細 | 調理支援 | 人数切替、材料(分量)、作り方、「+1品」提案、「買い物リストに追加」、「食べた」、ハート、「…」(出さない料理に追加、レシピを検索) |
| 買い物リスト | 買い物 | 料理別にまとめた材料、チェック、手動追加。二人モード時は共有 |
| 履歴・お気に入り | 振り返り | 食べた日付順、お気に入り一覧、自分の写真 |
| 設定 | 条件 | 人数、標準の時間、苦手食材、予算、出さない料理、ふたりで使う(招待・解除)、データ書き出し |
| 相手待ち(二人) | 待機 | 「Bさんの回答を待っています」、「ひとりで決める」 |
| 歩み寄り(二人) | 不一致 | 二人の1位、「今日は譲る」「コイントス」「両方作る」 |

- タブは「決める / 買い物 / 履歴 / 設定」の4つ。
- 「決める」の流れは常にフルスクリーンで、決まるまでタブを隠す。

## 9. リリース計画

### v1.0(最小構成: 1人で、短時間で決まる)

- 1人モードの決定フロー一式(気分・時間、勝ち抜き二択、別候補2回、おまかせ、決定画面の材料チップ)
- 料理データ150件(A層+B層、イラスト)
- フィルタとスコア、2段階の緩和、学習(選択のみ)
- 料理詳細(人数換算、+1品、レシピ検索ボタン)
- 買い物リスト、食べた履歴、お気に入り、自分の写真の差し替え
- 設定、オンボーディング1画面
- データは端末内のみ。iCloudバックアップに含まれる
- 任意・匿名の利用統計

### v1.1(ふたりで使う)

- ペアリング(Appleでサインイン、招待リンク)
- 二人モードの決定フロー、一致判定、歩み寄り
- 共有の買い物リストと履歴、「疲れた」「私が作る」の合図
- プッシュ通知
- 料理データ+20件

### v1.2以降(需要を見て)

- 自由入力の気分(端末内モデル)
- 料理データの差分配信(Supabase Storage)
- 週まとめ買い(数日分を先に決めて買い物リストを合算)

### 入れないもの(意図的に)

- 本格レシピ、動画、栄養計算
- ユーザー投稿レシピ(審査・権利・運用負担が個人開発に合わない)
- 「端末を渡す」「リンクで選択を送る」方式の二人モード(ペアリング方式に置き換え)
- SNS共有機能、広告

## 10. 収益化(決め: 無料 + 買い切りPro 500円)

| 区分 | 内容 |
| --- | --- |
| 無料 | 1人モードの決定フロー全部。料理68件。履歴30日。買い物リスト |
| Pro(買い切り 500円) | 料理全件(150件+追加パック)、ふたりで使う(招待する側のみ必要)、履歴無制限、自分の写真差し替え |
| 追加パック(非消耗型) | 200〜300円。例:「鍋20選」「お弁当おかず20選」 |
| 公開直後の割引 | 最初の1〜2週間は Pro を300円で出し、レビューと利用者を先に集める |

### 価格の考え方

- 運用費はユーザーが増えても増えない。Supabase と Apple Developer Program は他のアプリのために契約済みで、1人モードは通信しない。1人増えるごとの費用はゼロ。
- それでも価格は原価ではなく「迷わず押せるか」で決める。日本の App Store で「とりあえず買う」が起きる境目は500円前後。800円以上は献立アプリには重い。
- 二人モードは招待する側だけが Pro を買うので、Pro 1本で使う人が2人増える。価格は広がる速さを直接決める。
- 160〜250円まで下げると「おもちゃ」に見えて信用を落とす。サポートの手間は価格に関係なく1人分かかる。
- Apple の手数料15%(Small Business Program)を引いた手取りは1本約425円。

### 方針

- 決める体験自体は無料で完結させる。無料68件でも除外なしの全組み合わせで14件以上残ることを検証済み。
- 二人モードは招待する側だけ Pro。招待された側は無料でよい。
- サブスクリプションは、月ごとの料理追加や実行時AI費用が発生するまで導入しない。
- 広告は入れない。
- 買い切りで二人モードを売る以上、Supabase の契約を止めると二人モードが動かなくなる。契約を見直すときは事前に移行先を決める。

## 11. 技術構成

- Swift / SwiftUI。iOS 17以上
- 永続化: SwiftData(またはCore Data)。料理データは同梱JSONを初回起動時に取り込み
- 画像: アプリ同梱のアセット(イラスト150枚、1枚200KB以下)
- 二人モード: Supabase(Auth は Appleでサインイン、Postgres にペア・回答・共有リスト、Realtime で相手の回答を受信、Edge Function からプッシュ通知)。Row Level Security でペアの二人だけが読める
- 1人モード: サーバー通信なし
- 計測: 端末内集計+任意の匿名送信
